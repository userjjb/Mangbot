# Dispatch: game-mechanics changes 2010 -> 2018 (v1.1.2 -> v1.1.3/v1.1.4 -> v1.4.0, plus the master-branch burst)
- Brief: list gameplay changes in the 774-commit span; say what 1.4.0 and the 2015-16 burst changed for a player; say which forum advice they date.
- Clerk run: 2026-09-29; sources: all 774 subjects in scratch/V2_commits.txt (read in full); ~45 diffs opened; `git diff v1.1.4 v1.4.0` and `v1.1.2 v1.1.4` stats; 1.5.3 source at github/src/server and tag v1.5.3 for checks; forum memo §1-§4, Addendum A-C.

## Answer
The span holds very little gameplay change. Of 774 commits, roughly 700 are the netcode/UI rewrite (#952 streams, #962 indicators, #963 custom commands, #964), build/VS/Travis/Coverity work and whitespace. The gameplay changes are about 30 small items. The "1.4.0 jump" is a version label, not a big change: v1.4.0 is v1.1.4 plus 26 commits (~600 changed lines, Nov 29 - Dec 1 2018) from Graham King. Its player-visible content: wands, staffs and rods stack and share charges, per-character artifact preservation, a free Word of Recall for every class, and auto-retaliate no longer fires while afraid. The real jump for our bot is v1.5.0 (1619 commits after v1.4.0). It carries the whole 2010-16 master-branch rewrite, which was never released as 1.1.x. Almost all of that is protocol/UI. Old forum mechanics (monster.txt, spells, damage) are unchanged in this span.

## Structural finding first (changes how to read the span)
1. There are two lines. [SEEN] v1.1.3, v1.1.4 and v1.4.0 are on the "stable" line (branched from 1.1.2 with `git-svn-id .../branches/version-1_1_3`). The master/trunk rewrite (`cd09022` 2010-03-15 "replaces XPilot code with our own... breaks everything big-time") first appears in v1.5.0. `git merge-base --is-ancestor`: cd09022, 951b441 and c4078e4 are ancestors of v1.5.0 only; v1.4.0 is an ancestor of v1.5.0. Tagging my 774 commits by the earliest tag that contains them gives: v1.1.3 = 36, v1.1.4 = 38, v1.4.0 = 26, v1.5.0 = 672, v1.5.3 = 2. Most 2015-16 "burst" commits (flambard-took, e.g. 951b441 looking/targeting, e4b5d13 store "confirm" packet) are master, hence 1.5.0.
2. The 2016 releases 1.1.3 (tag 2016-03-31/04-05) and 1.1.4 (2018-11-22..29) were fed by porting fixes from trunk ("Ports rNNNN from trunk to stable").
3. `lib/edit/*.txt` (monster, object, artifact, class, race, vault, terrain) are **byte-identical** v1.1.2 -> v1.1.4 -> v1.4.0 except the `V:` version stamp [SEEN: `git diff v1.1.4 v1.4.0 --stat`; 32 files, only server .c and mangband.cfg differ]. So no monster/item/class table changed in this span on the stable line. The one data change is the master-only `p_class.txt` reorder (`3e3fc1e`). I checked its `B:` lines per class before/after: same multiset for all 5 casting classes, so it is a pure re-ordering (spell stats unchanged) [SEEN via script].

## Contradictions and surprises
1. **1.4.0 is not a superset of what 1.5.3 does.** Three 1.4.0-era changes are absent from 1.5.3 even though 1.4.0 is an ancestor of 1.5.0: shortened blind/hallucination (`438e1eb`), the monster-energy `else` branch (`1789855`, which is an ancestor of v1.5.0 yet absent from the code), and the artifact-preservation enum/default (changed from default 2 to 3 with different numbering). [SEEN: greps above.] Likely cause is merge resolution taking master's `use-obj.c`/`melee2.c`; I did not read the merge commits, so the cause is [INFERRED].
2. **Artifact preservation in 1.5.3 may be a no-op.** `object2.c:2251` blocks generation only if `p_ptr->a_info[i] > cfg_preserve_artifacts`; the maximum state is `ARTS_SOLD = 3` and the default cfg is 3, so the condition is never true [INFERRED from the two constants; not run]. The 1.4.0 test was `>=` with default 2. The live server's `mangband.cfg` value is unknown. Advisor should have V3 confirm.
3. The brief expected 1.4.0 to be a "big jump". The diff says otherwise: 26 commits, +607/-209. The number appears to be a rebrand to mark a "development" stream (`VERSION_EXTRA` 0 -> 3 in `defines.h`); the 1.2/1.3 numbers were skipped. [SEEN `defines.h` diff.]
4. Memo Addendum B says Healing potions "scarce". For a short period in 2018-19 the Temple sold them; by 1.5.3 that was undone. The memo is right for our target version but would be wrong on a 1.4.0 or 1.5.0-1.5.2 server (I did not verify 1.5.1/1.5.2 contents; only that v1.5.3 contains the revert).
