# Dispatch: V1 game-mechanics changes, 2005-11 to 2009-12 (0.7.2a to v1.1.2 and the trunk after it)
- Brief: list the gameplay changes in the 1256-commit span, say what a player of the previous version would notice at the end of the span, date five named mechanics, and flag forum advice that is now outdated or confirmed.
- Clerk run: 2026-09-29. Sources: all 1256 subjects in `scratch/V1_commits.txt`; diffs and `git grep` on tags in `data/versions/upstream/` (repo hashes are cited); forum memo `memos/2026-09-26-forum-distillation.md` (read in full); 1.5 source `github/src/server/`. `xtra2.c` line numbers in the 1.5 source are in the working tree; every other line number is at the named tag or commit.

## Answer
1. **The span is not one line of releases.** Only 527 of the 1256 commits are ancestors of tag `v1.1.2` (2009-04-27). The other 729 are trunk commits made after the 1.1 branch split, running to 2009-12-24 (`77d14cc`). That trunk work was first released in **v1.5.0** (2019). v1.1.3, v1.1.4 and v1.4.0 do not contain it. Each row below is marked "in 1.1.2" or "trunk only (first release 1.5.0)".
2. **Four of your five named mechanics were already present in the 0.7.2a import or the 1.0.0 merge.** Connected stairs and level persistence are in the original import (`1400c6e`, 2005-11-15) and have not changed since. Hound clearing on arrival came 2005-12-09 (`46737ea`). Per-character uniques came with the 1.0.0 merge, 2007-11-14 (`7b06c5c`).
3. **The time bubble is the only one of the five that is late.** It was committed on trunk 2009-05-07 (`f01053d`). It is not in v1.1.2, v1.1.3, v1.1.4 or v1.4.0, and first ships in v1.5.0.
4. The biggest player-visible changes for a 0.7.2a player upgrading to 1.1.2 are: a rewritten monster list (549 to 620 races), unique kills tracked per character, hound clearing, the Angband 3.0.6 item/spell/stat tables, store and Black Market changes, no haggling, and player-owned shops. Details follow.

## Findings

### A. The five named mechanics, dated
1. **Connected stairs: present in the 0.7.2a import, unchanged through 1.5.3.** [SEEN]
   - `alloc_stairs()` records `level_down_y/x` at each `FEAT_LESS` and `level_up_y/x` at each `FEAT_MORE` (`1400c6e:src/server/generate.c:556-581`).
   - `dungeon()` starts the player at that spot: LEVEL_DOWN uses `level_down_*`, LEVEL_UP uses `level_up_*`, LEVEL_RAND uses `level_rand_*` (`1400c6e:src/server/dungeon.c:1964-1977`).
   - The placement loop tries `scatter()` at distance `(j+149)/150`, which is 0 for the first tries, so the player lands on the stair grid itself (`dungeon.c:2009-2018`). [INFERRED from that arithmetic]
   - You arrive on a designated stair of the opposite type after `>` or `<`, and no stair is created under you.
   - `dungeon_stair` ("Generate dungeons with connected stairs") is a dead option. It appears only in `tables.c`, `variable.c` and `externs.h` at 0.7.2a, v1.1.2 and v1.5.3, and nothing reads it. Connected stairs cannot be switched off.
   - The same `level_down_y` code is in v1.5.3 (`generate.c:632,645`, `dungeon.c:2128`).
2. **Level persistence: present in the 0.7.2a import, unchanged.** [SEEN]
   - A level is freed only when `players_on_depth[j]==0 && cave[j]` (`1400c6e:dungeon.c:1892-1897`).
   - `LEVEL_UNSTATIC_CHANCE = 30` is in `1400c6e:mangband.cfg:72` and in the v1.5.3 `mangband.cfg`.
   - The same structure is in v1.1.2 and v1.5.3.
3. **Hounds cleared on arrival: 2005-12-09, commit `46737ea`, "Insta-death on recall and stairing fix".** [SEEN]
   - The commit message reads "Remove hounds immediately around the player when entering a new level."
   - The code is a `switch (p_ptr->new_level_method)` over `LEVEL_DOWN` and `LEVEL_RAND` only, with the comment "we don't want to make stair scuming safe". It deletes non-unique monsters with `d_char=='Z'` within `MAX_SIGHT`.
   - `b53ee77` (2005-12-15) fixed the distance test. `cdis` had not yet been computed, so the first version deleted nothing reliably.
   - The code is identical at v1.1.2, `77d14cc` and v1.5.3 (`dungeon.c:2211`).
   - The author field says **gray**. The memo says "Jug wrote it for IronMAngband ... ported in 2006". The repo has no commits between 2005-12-27 and 2007-10-29, so "ported in 2006" cannot be checked here.
4. **Per-character uniques: arrived in the 1.0.0 merge `7b06c5c` (2007-11-14).** [SEEN]
   - The parent `e03a73b` has no `r_killed` or `allow_unique_level`. The merge adds `allow_unique_level()`: a unique may spawn only if some player on the level has not killed it (`monster2.c`). It also adds `p_ptr->r_killed[]`.
   - The old global respawn timer block in `dungeon.c` is wrapped in `#if 0` with "don't announce".
   - Repeat kills give nothing: `xtra2.c` has "Cheezy kills give neither xp nor loot!" (`7b06c5c:xtra2.c:3021-3023`; present in 1.5.3 at `xtra2.c:2935,3008`).
   - Before this, uniques were global. Death of the killer revived them (`r_ptr->killer == p_ptr->id`, `1400c6e:xtra2.c:2210-2218`), or a `BASE_UNIQUE_RESPAWN_TIME=200` timer did (`dungeon.c:1640-1668`).
   - `10dbaae` (2007-12-01) made a death reset your own kills. `8710263` (2007-12-02) limited that to uniques above `max_dlv - 35%` (`max_dlv*11468>>15`), "as a balance issue".
   - `0178d51` (2009-04-11) made Morgoth ("Never respawn Morgoth", `RF1_DROP_CHOSEN`) never return. That is present in v1.1.2 by content.
   - The reset runs in `player_death()` (1.5.3 `xtra2.c:2706`), on any death, not on resurrection.
5. **Time bubble: trunk only, `f01053d`, 2009-05-07 ("Merges timebubbles branch back into trunk", ticket #689). First release v1.5.0.** [SEEN]
   - `bubble_speed` appears in 0 server files at v1.1.2, v1.1.3, v1.1.4 and v1.4.0, and in 1 file (`src/server`) at v1.5.0. `f01053d` is not an ancestor of v1.4.0.
   - Two earlier trunk attempts fell short. `8449675` (2008-08-22) raised energy resolution 100 times and was reverted by `c792e22` the same day. `509d4c7` (2008-08-21) made a monster's turn use energy.

### B. Time-bubble details (first version, `f01053d` diff)
- If HP% is at most `hitpoint_warn*10`, time scales by HP% (floor 10%). Resting gives 10× time. In 2009 that held even with monsters in view; 1.5.3 requires no monster in line of sight (`xtra2.c:5201-5205`). [SEEN]
- A chain of players within `MAX_SIGHT` takes the slowest bubble. The different-level test compares `p_ptr->dun_depth` to itself, so the first version linked players across levels. [SEEN]
- Running in the dungeon sets 500% and scales monster energy too (`melee2.c` diff). In 1.1.2 a run step cost `level_speed/5` energy (5× walking for the runner only). After the merge each step costs a full turn and the bubble runs 5× faster, monsters included. [INFERRED from the diff]
- The player energy cap fell from `2*level_speed-1` to `level_speed`. Mana regeneration lost its `*5/3` factor and the resting multiplier fell from ×3 to ×2.
- `hitpoint_warn` was ported from Vanilla as the threshold (`785efa8`, 2009-04-23).

## Contradictions and surprises
- **Author and timing of the hound fix.** The memo credits Jug and "ported in 2006". The repo commit `46737ea` is by "gray" on 2005-12-09, and the 2006 port cannot be confirmed (no 2006 commits in the repo). The fix is in every release from 1.0.0 on, and in 1.5.3.
- **Memo Addendum 3 #1 says uniques come back "when a character is resurrected".** In code the reset is in `player_death()` (1.5.3 `xtra2.c:2706`), so it happens at death whether or not the ghost is later resurrected. The 65%-of-max-depth threshold in the memo is correct.
- **"v1.1.2 is the end of the span" is wrong.** The commit list runs to 2009-12-24 and includes 729 commits not in v1.1.2. v1.1.3 (2016) and v1.1.4 (2018) are stable-branch releases with none of them.
- **Connected stairs and level persistence are not "later" features.** The `dungeon_stair` option looks like a switch but does nothing.
- **Time bubble bug.** The first version's cross-level test compares a player's depth to itself, so players on other levels within range were linked into the chain. I did not check the 1.5.3 code for this.
- **Ancestry is unreliable as a version test.** The 1.1 branch got ports as separate commits ("Port rNNN from trunk to stable"). Many trunk commits are in v1.1.2 by content but not by ancestry (for example `feda14a`, `ff9ce12`, `0178d51`, `9a7d3c6`, `b40cb36`). I checked by grepping the tag tree wherever a row depends on it.

## Leads
- Other clerks should not treat v1.4.0 as "trunk 2009". Its ancestry omits 2009 trunk work such as `f01053d`. That is a version-line question for V2/V3.
- `MAGE_HITPOINT_BONUS` (present in the 2009 `mangband.cfg`, absent in 1.5.3): I did not find the removal commit.
- I did not open the 1.0.0-merge item, ego and artifact lists (`k_info`, `e_info`, `a_info`) beyond their diffstat. A fresh diff of the tagged data files against 1.5.3 would show the item-level changes.
- I could not confirm what "limited ESP" (memo E, t=1568) means in this repo. The merge adds `TR4_ESP_*` flags, but they sit under `NEW_ADDITIONS` and were stripped by `5e86f89`.
- Running got expensive in 1.1.2 too: `run_step` bumped the cost to `level_speed/5` per step. A live test of the current run speed against the memo's A7 would settle it.
