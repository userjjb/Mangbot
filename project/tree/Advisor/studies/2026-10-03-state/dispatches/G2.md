# Dispatch: G2 - the client and tool mode: what state the bot can read
- Brief: map every `recv_*` handler to the client state it updates; list every tool-mode event and query and how each is produced; explain streams/indicators; check against pkt.jsonl; list known gaps.
- Clerk run: 2026-10-03; sources covered: src/client/net-client.c (all 2557 lines), net-client.h, c-tool.c (all 896), c-pktlog.c, parts of c-init.c/c-xtra2.c/c-files.c; server src/server/tables.c (stream+indicator tables), xtra1.c (prt_* senders), object1.c (inven send), net-game.c (send_indication), cave.c (cursor), monster2.c (monlist); runs/observe/session{1,2,3}/pkt.jsonl (+ session3 screens.jsonl); runs/pilot/dive0*/events.jsonl (sample). Scratch scripts: Advisor/studies/2026-10-03-state/scratch/.

## Answer
Tool mode exposes state in six ways: a `status` query (all indicator "coffers" as numbers, keyed by indicator mark), an `inven` query (pack + equipment: slot index, name text, tval, count, total weight), a `map` query (the dungeon stream as chars + colour attrs), the pushed events `pos`/`level`/`message`/`monlist`/`itemlist`/`store`, and `minimap`/`options`/`commands`. Almost every number is a raw number in `status`; items, floor, monster list and level feeling are only text. The server sends numeric indicators, not rendered text, so "level as (max, current)" is `ind.level = [max, cur]`. Inventory arrives per dirty slot (the changed slot to the end of the pack when the pack shifts), with "(nothing)" rows for empty slots. The most dangerous trap is that the `depth` indicator is a signed byte, so in the wilderness it is a wrapped garbage value (see Finding 1).

[SEEN] The tail -113, -85, -61, -41, -25, -13, -5, -1 is the first index of rings 8 to 2 of the world_index spiral (ring r starts at 2r^2-2r+1). The only real wilderness position source I found is the `minimap` frame ("[14N, 2W]", `c-tool.c:49-56` header comment; not verified here).
2. **Level and exp.** `prt_level` sends `(MAX(max_plv, lev), lev)` (`xtra1.c:166`), `ind.level = [max, cur]` (LEVEL TINY, amnt 2, `tables.c:585`). `prt_exp` sends `(max_exp, exp, adv_exp)` (`xtra1.c:181`); `adv_exp` is the absolute exp needed for the next level, not the remainder. [SEEN] Wire: login `level c3 01 01` = (1,1); `exp` = (0,0,11); at level 4 `exp` (70,70,77) (session1 t=849.6). In all 3 sessions max==cur always, so a drained case was never observed. [SEEN log] `level`+`exp` are re-sent together roughly every 1.2-2.7 s median gap; 82 of 90 level packets in session 1 were identical to the previous one. So the packet being re-sent says nothing about change.
3. **Stats = three numbers: `[stat_use, stat_top, stat_max_or_top+1]`.** `prt_stat` (`xtra1.c:104-124`) sends `stat_use`, `stat_top`, and (only if the natural max is 18/100) `stat_top`, otherwise `stat_top+1`. So the third value is not the natural max; drained = use < top. Wire: stat0 (68,68,69) normal; (58,68,69) at session1 t=1794 (drained); stat3 (28,28,29) then 18,17,...,5 against top 28 in session 2 at t=1068-1117. Encoding is raw Angband 3..118 (18/50 = 68). [SEEN code + log]
4. **Status conditions are bucketed ints, not durations.** Indicator semantics (all `xtra1.c` prt_*): hunger 0..5 (0 faint, 1 weak, 2 hungry, 3 normal, 4 full, 5 gorged; `xtra1.c:239-279` and label text `tables.c:719`); cut 0..7; stun 0..3; blind/confused/afraid/poisoned/study 0/1; `state=[paralyzed, searching(0/1/2), resting]`; `speed = pspeed - 110` with the search slowdown undone (`xtra1.c:407-413`; wire -10 at session1 t=991); `armor=[total, base, to_a]`; `hp=[cur,max]`; `sp=[cur,max]` ((0,0) for non-casters); `oppose=[acid,elec,fire,cold,pois]` (turns left, nonzero); `track=[attr,len]` = health bar of the tracked monster only (attr colour: blue asleep, violet afraid, red..green by pct; len 1-10; `xtra1.c:1346-1407`). `skills2=[blows, shots, infravision]` (`xtra1.c:1143`); `plusses=[to-hit, to-dam]`. No indicator exists for: word-of-recall pending, hero/bless/shield/haste/slow timed effects, see invisible, free action, light radius, burden, game turn, level feeling. [SEEN: full table `tables.c:567-780` has none of these]
5. **Inventory wire format and update granularity.** PKT_INVEN = `pos letter, glyph a, glyph c, attr, weight u16, number s16, tval, flag, tester, name, name_one` (`net-client.c:2015-2018`); all multi-byte ints are big-endian (verified by decoding: 7 Rations = `0046`=70 weight, `0007` count). `weight` is the whole stack's weight in 1/10 lb (`object1.c:2943`: `wgt = o_ptr->weight * o_ptr->number`). The server only sends slots whose bit is set in `redraw_inven` (`object1.c:2920-2923`). Observed:
   - Login: all 24 pack slots a-x (empty ones as `(nothing)`, tval 0, number 0) plus 12 EQUIP slots a-l. INVEN_PACK=23, INVEN_WIELD=24, INVEN_TOTAL=36 (`server/mdefines.h:702-723`): pack letters a-x are 24 slots, equipment array indices 24-35.
   - Pickup into a free end slot: one packet (session1 t=195.406, 'e' = Small Metal Shield; message "You have a Small Metal Shield ... (e)").
   - Stack decrement (eat, read): one packet (t=650.98 `a` 7 Rations; t=560.206 `f` scroll 2->1).
   - Item used up / sold / destroyed: the emptied slot and every later slot are re-sent (the pack compacts): t=562.302 `f..x` (19 packets), t=237.937 `g..x`, t=1125.058 `j..x`. A slot's contents can therefore change identity without any message naming it, so slot letters are not stable across any item removal.
   - Group-size histogram of PKT_INVEN bursts (<=3 ms apart): session 1: 31 single, 9 pairs, 6 triples ... 10 full bursts of 24; session 2: 24 singles, 10 pairs, ... 3 of 24; session 3: 7 singles, 4 pairs, 3 triples, 18-24 bursts. [SEEN]
   - Light fuel: the lit lantern/torch slot is re-sent as PKT_EQUIP at every 100 game turns (`dungeon.c:1488-1498`: `pval % 100 == 0` or `< 100`), name text "Brass Lantern (with 14800 turns of light)"; observed every ~25-45 s, e.g. t=674.39 14900, 713.6 14800 ... [SEEN]
   - Inscriptions, charges, to-hit/dam, pseudo-ID ("{average}"), turns of light all exist only inside the `name` string; there is no structured field. The client also stores `ident=flag` and a "tester" byte (item_tester bits) but tool `inven` does not output them (`c-tool.c:533-539`).
6. **Depth change on the wire** (session1 t=751.649-751.657): client sends `CUSTOM '>'`; ~2 ms later the server flushes the remaining old-level cell updates, then `PKT_MESSAGE "You enter a maze of down staircases."`, `PKT_SOUND`, level-feeling message "This level can't be all bad.", then the new level's streamed cells/lines, then `PKT_CURSOR` (new position), then `IND:depth` LAST (`da 01`), then `PKT_FLOOR` (empty). Everything is within ~8 ms. Latency command to depth packet: 7-15 ms in session 1. So the new map and the new depth are not atomic on the wire; the depth indicator trails the map. The tool's `level` event is generated per loop iteration after the whole read is parsed (`c-tool.c:877-895`), so in practice map, pos and level are consistent when the Pilot reads them after the `level` event. But a `>`/`<` that lands on the same depth number produces no `level` event (`c-tool.c:852`). [SEEN log + code; the "same depth, no event" case INFERRED from code]
7. **How often status packets arrive** (R packets, counts for session 1/2/3, durations 1920/2185/741 s): HP 926/411/21 (about 29/min in session 1; 55% identical to the previous); `track` 405/384/16; `level` and `exp` each 90/102/12; `depth` 93/49/19; `gold` 37/59/14; `skills`+`skills2` 111/125/23 (mostly identical repeats); `state` 59/17/2; `speed` 4/13/1; `hunger` 6/6/1; `armor` 12/10/2; stats 3/19/1 each. KEEPALIVE 1/s both ways. Indicators are pushed on change (flagged via `p_ptr->redraw`), so a missing packet means unchanged, except level/exp/skills which are over-sent. Wire totals: session 1 had 65,267 R packets of which 51,829 (79%) are DUNGEON_ASCII stream rows/cells.
8. **Position.** `PKT_CURSOR` from `cave.c:1543` sends `(MCURSOR_PLAYER, y, x)` with the player's absolute dungeon coordinates, but only when the player's own grid is redrawn (it is always redrawn since the test includes `x==px && y==py`, `cave.c:1531-1535`). When the player is outside the shown panel the server sends `MCURSOR_PLAYER|MCURSOR_OFFLINE, 0, 0` (`cave.c:1553`), which tool mode ignores (`c-tool.c:390`), so `status.y/x` and the last `pos` stay stale in that case. Handler hack: payload bytes arrive as (y,x) while the C parameter names are (x,y) (`net-client.c:1716-1718`). The panel offset is never sent; the map stream is a scrolled window, so the Pilot has to locate `@` in the `map` rows to relate stream coordinates to absolute ones. [SEEN code; "panel offset never sent" INFERRED from not finding any packet that carries it]
9. **Monster list is names and counts only.** `display_monlist` (`monster2.c:724-840`) emits one line per visible race: `Name ('d_char')/('visual_char'):[count]`, then visible players as "Name, the Race Title ('c')". No position, distance, health, sleep or awake. Pilot logs agree: `"Snaga ('o')/('o'):[2]"`, `"You see no items."`, `"You can see 1 item:", " ! Cloudy Potion"` (runs/pilot/dive0*/events.jsonl). Per-monster information has to come from the map stream glyph (tool mode can set unique race glyph/colour pairs via `--visuals`, `c-tool.c:166-217`) plus the single tracked-monster health bar. [SEEN]
10. **Store event ordering.** Server sends the N `PKT_STORE` item packets, then `PKT_STORE_INFO` (count/name/owner), then repeats items after a purchase/sale (session1 t=256.03: STORE x28, INFO, STORE x28). Tool emits a `store` event once per `STORE_INFO` via `enter_store` (`net-client.c:575-580`, `c-tool.c:367-371`, built from `store.stock[]`, `store_names[]`, `store_prices[]`). If the trailing STORE packets land in a later TCP read than the INFO packet, the event could carry pre-update items. [INFERRED from code; not observed]
11. **Message handling.** `do_handle_message` in tool mode emits `message{type,text}` and returns (`c-xtra2.c:306-310`); `recv_message_repeat` re-emits the last message (`net-client.c:1807-1821`). Inventory letters and "You have no more ..." are only in message text. Level feeling and recall are only message text.

## Tool-mode events and queries (Q2), all c-tool.c
- Loop (`c-tool.c:861-896`): each iteration = `network_loop()` (parse ALL buffered packets; pos/message/monlist/itemlist events are printed from inside this) -> `tool_process_requests()` (pause, local_browser, popup, interactive, confirm, store, store_leave events) -> `tool_check_level()` (level event) -> `tool_poll_stdin()` (up to 256 bytes; every complete line is executed immediately and its reply printed) -> `flush_updates()`. Single-threaded; no caching of game state except `tool_py/px`, `tool_last_depth`, the static `ind` index.
- Events: `ready{nick,door,visuals}`; `message{type,text}` (221); `popup{header,lines[]}` (230); `monlist`/`itemlist{lines[]}` pushed when the server refreshes those windows (255); `pause`; `local_browser{header}`; `interactive{header}` (ESC sent back); `confirm{type,id,prompt,answer}` (declined unless `confirm yes` within 5 s); `store{flag,name,owner,num,items[{slot,name,number,price,weight,ga,gc,attr}]}` (290); `store_leave`; `blocked_input{where}`; `pos{y,x}` only on change and only for non-offline cursors (383); `level{depth}` on `depth` indicator change, and once at start (837); `ack{cmd}` = command written to socket, NOT executed; `error{text,cmd}`.
- Queries: `status{y,x,ghost,ind{mark:[..]|"string"}}` (484; all indicators including clones such as `hist_level`, `hist_mhp`, which are windows onto sub-coffers), `inven{items[{item,equip,name,tval,number,weight}]}` (519; skips tval 0, so empty slots are omitted, `item` is the raw array index, equipment starts at 24), `map{stream,wid,hgt,rows[],attrs[]}` (545; the dungeon stream as stored, attrs chr(48+attr)), `minimap{rows[]}` (777; needs the minimap stream subscribed by `custom M`), `options`, `commands`.
- Ordering: a `status`/`inven` reply reflects the client state at the last completed `network_loop`. Two commands in one stdin chunk execute with no network read between them, so `walk 4\nstatus` returns pre-walk state. Because replies print synchronously while pos/message print while parsing, a reply can sit between two events that belong to the same server burst.
- Stale-data risks in tool code: (a) `tool_py/px` after OFFLINE cursor; (b) `status.ghost` ok but `fruit_bat` not exposed; (c) indicators default to 0 before the first packet (`coffers[]` zero); (d) `level` event keyed only on the depth number (Finding 1, 6).

## Streams and indicators (Q3)
The server defines 12 streams (`tables.c:454-529`: DUNGEON_ASCII/GRAF1/GRAF2, MINIMAP_ASCII/GRAF, BGMAP, SPECIAL_MIXED/TEXT, MONSTER_TEXT, MONLIST_TEXT, ITEMLIST_TEXT) and ~70 indicators (`tables.c:567-956`), sent to the client at login via PKT_BASIC_INFO modes (`net-game.c:1274-1278`); the client then registers a handler per packet id (`net-client.c:1151-1156, 1516`). Indicators carry numeric values (TINY=signed byte, NORMAL=s16, LARGE=s32, STRING); the text in the `prompt`/format field (e.g. `"LEVEL \aG%6d\f\r\vLevel \ay%6d"`, `tables.c:586`) is only a client-side rendering template that picks which coffer to show. Tool mode ignores the templates and returns the coffers, so nothing arrives only as rendered text in tool mode except: map/minimap/monlist/itemlist/popup rows (streams: chars+colours), `inventory_name` strings, `race_/class_/title_/hist*/name` string indicators, and messages. Streams the tool mode subscribes to: dungeon, special (popups), monlist, itemlist (`c-init.c:810-816`); minimap only after `custom M`.

## Check against reality (Q4): pkt.jsonl format
One JSON object per line (`c-pktlog.c:1-17`). Fields: `t` seconds since client start; `dir` R (server to client, one record per parsed packet), S (client to server, one record per flushed chunk, keepalives split out, the first 2 bytes are a "HANDSHAKE" conntype), E (note: e.g. `pktlog started epoch=...`, `connected to server`), K (a key consumed by a command: `key, code, keymap, icky`, or `muted:true` for password keys); `id` packet id; `name` (R: PKT_ name, or `STREAM:<mark>` / `IND:<mark>` for dynamic ids; S: custom commands as `CUSTOM:'<key>'`); `len` bytes including the id byte; `res` parse result (1 normal, 2 "break the network cycle"; 2 packets in s1, 1 each in s2/s3); `hex`; `txt` printable view. Numbers are big-endian. meta.json per session holds start epoch, command line, frame count. Caveats: sessions are a human on the curses client (`-mgcu`, meta.json cmd), not tool mode, so there are no tool events and K records exist; session durations 1920/2185/741 s; line counts 72,794/122,968/34,667; no malformed lines. Packet counts, top entries (s1 / s2 / s3): STREAM:DUNGEON_ASCII 51,829 / 97,299 / 24,587; PKT_CURSOR 3,055 / 4,275 / 1,706; PKT_KEEPALIVE 1,692 / 2,050 / 652; PKT_MESSAGE 1,119 / 979 / 147; PKT_STORE 1,031 / 2,901 / 868; PKT_INVEN 907 / 953 / 223; PKT_EQUIP 72 / 112 / 43; IND:hp 926 / 411 / 21; PKT_FLOOR 186 / 118 / 29; PKT_OBJFLAGS 455 / 507 / 195 (full list produced by `scratch/cnt.py`). Session 3 also contains the only STREAM:MINIMAP_ASCII packets (132) and `PKT_TERM_INIT`/`PKT_KEY`/`PKT_LOCATE` sends.

## Known gaps (Q5): server sends it, tool mode drops it
- Floor object under you (`PKT_FLOOR` into `floor_item`/`floor_name`; no query; only the "You see ..." message). Floor piles (pos > 0) are discarded by the client itself (`net-client.c:1985-1989`).
- Resist/ability grid (`PKT_OBJFLAGS` into `p_ptr->hist_flags`): this is where FA/SI/resists/sustains from equipment live, and tool mode never outputs it. [SEEN that it is stored and unused by c-tool.c; contents of the grid columns not read]
- Spell list (`spell_info`, `spell_flag`), item-tester bits, inventory `ident`/flag byte, glyph/attr of items.
- Target/look info (`recv_target_info`, target cursor), `PKT_PARTY` info, channel/chat membership, AIR and SLASH_FX effects, sounds, `fruit_bat`.
- Not sent by the server at all (so no source in either channel): recall pending, timed buffs (hero/bless/haste), see-invisible/free-action as live status, light radius, weight/burden, game time, level feeling as a value (only message).
- Monster details beyond the list (position, asleep, health except the tracked one).

## Contradictions and surprises
- Surprise vs "level is (max, cur)": confirmed (`xtra1.c:166`); but depth has its own problem (Finding 1), more serious than a display issue.
- Surprise: the brief assumes status as "rendered text". In 1.5 the numbers travel as numbers and tool `status` returns them; the rendered-text path is only for strings and rows.
- `c-tool.c:25-26` says `pos` is "absolute" and `level` "also once at start"; both hold, but `pos` is suppressed while offline-panel (Finding 8).
- I did not check how pilot.py / world.py consume these values (out of scope).

## Leads
- Pilot/Navigator code that reads `ind.depth` should be checked for the wilderness wrap (Finding 1) and for assuming `status.ind.level[0]` is the current level (it is the max).
- Needed: a server or client fix would be to widen DEPTH to NORMAL (s16) or add an indicator for wild position; the client could instead compute location from `minimap`.
- Inventory slot-letter instability on item removal (Finding 5) deserves a rule in the Pilot: re-read `inven` after any "no more"/sold/destroyed message.
- Check the pilot's `status` reply logs (none were found in events.jsonl; only events are logged there) to see how often status is polled versus pushed.
