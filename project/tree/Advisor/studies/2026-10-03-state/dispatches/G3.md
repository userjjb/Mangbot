# Dispatch: the Pilot's world model (G3)
- Brief: map every piece of game state the Pilot keeps (source, refresh, derivation, how it goes stale or wrong); list stale-value uses, duplicate sources, and the state-related git fixes since 09-27.
- Clerk run: 2026-10-03; sources covered: github/tools/pilot/{world.py, glyphs.py, mover.py, pilot.py} in full; tools/shopcat/mang.py:1-190; src/client/c-tool.c (status/inven/map/level/commands, 255-320, 380-896); server tables.c indicators, xtra1.c prt_*, object1.c display_inven/equip, cmd2.c stairs, spells2.c:1133-1200, dungeon.c light; client net-client.c recv_inven/equip/indicator/stream; observed pkt logs session1-3 (inven vs message order); dive03 decisions.jsonl; git log since 09-27. CSV: `/projectnb/jbrcs/mangband/Advisor/studies/2026-10-03-state/scratch/G3_state.csv` (48 rows: state, field, source, refresh, derivation, file_line, risk).

## Answer
The Pilot holds almost all state as a cache of what the tool-mode client emits. Events (pos, level, message, monlist, itemlist, store) are applied as they arrive. Three polled queries are re-read: status (indicators) every 0.3 s, map every 0.5 s or on a position change, inventory every 10 s or when `inven_dirty` is set. Six things are *derived* rather than read: `standing_on`, `in_dungeon`, monster identity (map glyph decode), depth in feet, `arrived_by` and `recall_pending`. These are the ones that go wrong. The inventory is the biggest hazard. The `inven` query only reads the client's own up-to-date copy, so the 10 s lag is the Pilot's own cache. Commands carry a slot *index* with no identity check. The Navigator's letters come from a report built on that cache.

## Findings
(Table in the CSV. Key items, most important first.)

1. **Inventory addressing is index-only, no identity check [SEEN].** `custom r item=N` sends a slot index (c-tool.c:433-450, pilot.py:1443). The server resolves it when the queued command runs. The Pilot picks the item from cached `w.inven` (`w.items()`, world.py:297-307), refreshed when dirty or every 10 s (world.py:222-225). Mission 9's WoR misread is this pattern (pilot.py:970-976 comment; commit 22a436d). The mitigation is `pending_use`: one read/quaff at a time, only for `USE_VERIFY` names and only in the dungeon (pilot.py:55-57,968-1028). Eat, fuel, wield, take off, destroy, inscribe and all agent verbs have no such guard.
2. **The dirty triggers miss several inventory-changing messages [SEEN].** `inven_dirty` is set only for messages starting "You have ", "You see ", "You are wearing/wielding", "Was wearing", "You destroy", "You feel", or containing "no more" or "in your pack" (world.py:143-147). The server also sends "Your X (c) was destroyed!" (spells1.c:892, fire/acid/cold), "Your X (c) was stolen!" (melee1.c:726) and "Your pack overflows!" (dungeon.c:1092). None of them match, so the cache stays stale up to 10 s. Letters shift after such a loss.
3. **The `inven` re-read can race the server's inventory packet [INFERRED].** In the observed human logs, "You have ..." arrives 0-1 ms *before* the PKT_INVEN update (session1-3, every one of ~32 sampled; mostly store buys). If the Pilot re-reads between them, `inven_dirty` is cleared on old data. The query is processed by the client after `network_loop` (c-tool.c:877-891), so same-batch packets are safe. A split TCP read is the risk.
4. **Agent verbs take raw letters at face value [SEEN].** `item_index()` turns a single letter into `ord(l)-97` with no check against the cache (pilot.py:2208-2213). The Navigator's letters come from `report()`'s Pack line, which is the cached list (pilot.py:2457), and Navigator think time can be minutes. `pack_now()` (pilot.py:2222-2230) re-reads 0.7 s after an agent action. That is not enough if the command is queued behind mover steps or the server is slow (INFERRED). By-name lookup uses a substring match on the *first* inventory hit, and names carry counts and plurals ("6 Scrolls of Phase Door"). So "Scroll of Phase Door" fails to match, and a loose "Cure" picks CLW before CSW (pilot.py:2268). `takeoff` with a single letter maps to a *pack* index, not equipment index 24+ (pilot.py:2211-2212, INVEN_WIELD=24 at mdefines.h:707). The report lists equipment without letters (pilot.py:2456), so letters aren't offered. Equipment slots have no names in the Pilot, only tvals (pilot.py:2113-2115). Rings (tval 45), ammo and diggers are not in `WEAR_TVALS`, so `wearall` ignores them.
5. **Depth has two sources that are never reconciled [SEEN].** `w.depth` comes from the 'level' event, which the client emits only when the depth *value* changes (c-tool.c:836-857). The status indicator `ind["depth"]` is polled every 0.3 s. Status only seeds `w.depth` when it is None (world.py:218-219). The server value is `dun_depth` as a signed byte (xtra1.c:234, net-game.c:384-388): levels, 0 = town, negative = wilderness. Feet are `depth*50` (world.py:15,263). In the wilderness `depth_ft` is negative or bogus, and the report prints "-N ft" for any non-zero depth (pilot.py:2447). The code itself notes that far wilderness wraps to positive (world.py:186-189).
6. **"Am I in the dungeon" has three definitions [SEEN].** `World.in_dungeon` is a heuristic over depth sign and how we arrived (world.py:186-201). Many sites test bare `w.depth` truthiness (pilot.py:704,743,1322,2002,2046) or `w.depth == 0` (pilot.py:370,667,2133,2282). In the wilderness (depth<0) the two disagree, e.g. `Shop` says "not in town" and `keep_light`/`town_light` treat it as dungeon.
7. **`recall_pending` is cleared by any level change, but the server's recall counter is not [SEEN code; INFERRED consequence].** The clear is at world.py:138. The server only zeroes `word_recall` on the trigger or on a second read (spells2.c:1190-1199). If a recall is read and the Pilot then takes stairs (emergency, flee), the Pilot believes none is pending. `recall_started()` falls back to a 5 s clock (pilot.py:1885-1890), so the next read *cancels* the recall. The Pilot does detect "A tension leaves" afterwards (world.py:170-172). `arrived_by` documents a 'recall' value that is never assigned (world.py:31 vs 128-135).
8. **`standing_on` has no ground truth [SEEN].** The map shows only '@' on your own square. The value is derived:
   - on a level event, from the stairs command sent <5 s earlier (connected stairs: opposite stair, world.py:128-135);
   - on a step, from `memory.get(new)`;
   - from message hacks (world.py:148-166).

   It is None at login, after a teleport or Phase Door (no step), and whenever memory lacks the square. A recall, trapdoor or Deep Descent within 5 s of a stairs command is misread as connected stairs. There is also a small race: `status()` overwrites `pos` (world.py:215-216) before the queued 'pos' event is drained. The drain's `new != self.pos` test then fails and `standing_on` is not recomputed (world.py:112-115) [INFERRED, rare].
9. **Monster identity is map-only [SEEN].** `w.monsters` is a decode of (char, attr) against a glyph table the Pilot builds from its *local* lib/edit/monster.txt and uploads via `--visuals` (glyphs.py:199-257, pilot.py:2555). The server's monlist is parsed (glyphs.py:259-268) but used only by `watch_perception` (pilot.py:1508-1531), a log-only diagnostic. `check_monlist()` is never called (grep). `w.monlist` is not reset on a level change (world.py:120-139). The map snapshot is ≤0.5 s old but compared with an event-fresh `pos`. Sleep, health (the `track` indicator), invisibility and visibility-vs-detected are not modelled. Undecodable glyphs (a monster not in the table, a mimic) are stored in `memory` as "objects lying on the floor" (world.py:240-241), so `goto item` and loot can target them. Evidence: dive03's decisions.jsonl has 9 `perception_gap` records; dive01, dive02 and dive04 have none. Several have `monsters: []` with a monlist entry present and map age 0.1-0.4 s (e.g. Snaga 'o' at depth 11, t=1790528138). The cause is not resolved (map lag vs a monster outside the map view).
10. **Map memory is add-only [SEEN].** Cells are written when seen, and nothing is deleted until the level event (world.py:236-241). The client's map stream is updated line by line and never wiped (net-client.c:1347-1399). The Pilot's first `refresh_map` runs in the same tick as the level event (world.py:126,207), so it may read the *old* level's rows into the new level's `memory` [INFERRED, not verified in logs]. Dive waits 0.6 s (pilot.py:327) but nothing else does.
11. **Character level is fixed; the pattern lives elsewhere [SEEN].** `clvl` = `ind["level"][1]` (world.py:274-281); the server sends (max(max_plv,lev), lev) (xtra1.c:166). The six raw `[0]` reads were replaced (commit 72ec098 diff). The other multi-field indicators are read at the right index: `armor[0]` is the total, `stat[0]` is current-use and `[1]` is top, `state[2]` is resting, `skills2[0]` is blows. `exp` ([max_exp, exp, adv_exp], xtra1.c:181) is never read.
12. **Conditions the Pilot can and cannot see [SEEN].** Server indicators exist for cut, hunger, blind, stun, confused, afraid, poisoned, state (paralyzed/searching/resting), speed, study, depth, oppose (elements) and track (tables.c:712-783). The Pilot reads blind, confused, afraid, poisoned, cut and stun via `flag()`, which is `bool(ind[name][0])` (world.py:283). Not read: paralyzed, speed in decisions (report only), `oppose`, `track`. No indicator exists for Hero/Bold/Bless/protection, slow, hallucination, free action or see invisible. FA/resists are hand-set orders (`free_action`, `resist_blind`, `resist_conf`; pilot.py:113-138,1127,1135,1608), never derived from equipment.
13. **Light fuel is parsed from the item name [SEEN].** The regex is `with (\d+) turns` (pilot.py:2022,2036,2048). The cache is ≤10 s old, but the server resends the slot every 100 fuel turns (every turn below 100, dungeon.c:1493-1500), so the client copy is fresh. Names are cut at 79 chars (object1.c:2902-2907 `o_name[80]`); a long lantern name plus inscription could lose the suffix [INFERRED]. Charges and counts exist only as name text. The Pilot never parses charges (grep).
14. **Position is single-sourced but dual-delivered [SEEN].** Both the pos event and the status poll read the client's `tool_py/px` (c-tool.c:394-402,489-490). The client suppresses 'pos' when the position is unchanged and when the cursor is "offline" (c-tool.c:389-394).
15. **Time is wall-clock only [SEEN].** All timers are `time.time()`, with the time bubble disabled (`--hpwarn 0`, pilot.py:2557-2563). Game turns, level feeling, other players and the exp indicator are not tracked.
16. **Messages are matched by regex on text, ignoring the message `type` field [SEEN].** c-tool.c:221-227 emits type; world.py:140+ ignores it. Several of the post-09-27 fixes were regex repairs (see 5 below).

### Q3. Every place a cached inventory value drives an action
`w.items()` / `w.inven` is read by:
- `escape()`: Phase Door `pd` (pilot.py:1415,1443,1484), Word of Recall (1432,1486), potion choice and `heal_of` (1469,1497), left-over check (1502)
- `group_tick()`: pd and WoR (1664,1676-1680)
- afraid handling (1267,1273); fearer phase (1302)
- `status_tick()` cure potions (1748-1755)
- hunger: `food[0]` (1318-1320, `eat N`)
- `keep_light`, `town_light`: worn light, flask, torch, spare (2005,2021-2052)
- `Recall` goal: item index and `recall_level(name)` inscription check (658-683)
- agent verbs `read`/`inscribe`/etc. (2268-2322); `do_request` WoR guards (2277-2286)
- `Shop` sells by letter or name (796-803)
- `auto_destroy` and `wear_step` (guarded by `inven_dirty`, 2064,2120)
- `report()` Pack and Equipment (2456-2457)

Only one has a use-confirmation loop (`pending_use`, pilot.py:968-1028). Counts: only `destroy`/`drop` use `number` (2072, 2289). Escape decisions use name presence, not count, so a stack that ran out reads as present until the "no more" message sets dirty. The `gold` check before a buy is guarded by `status_t=0` (779).

### Q4. Duplicates that can disagree
- depth: level event vs `ind['depth']` (finding 5); `in_dungeon` vs `depth` (6)
- pos: event vs status (8); map '@' unused
- monsters: map decode vs monlist (9); the `track` health indicator is unused
- `standing_on`: stairs-cmd assumption vs memory vs messages vs actual (8)
- `recall_pending` vs `recall_t` vs `Recall.read_t` vs the server counter (7)
- `clvl`: level[0] vs level[1] (fixed)
- inventory: cached `w.inven` vs the client's live copy vs "You have N X (c)" messages. Only `verify_use` reads the message.
- free action/resists: orders vs actual equipment
- `max_depth` order (feet) vs depth in levels vs the `@R` inscription (feet if divisible by 50, else levels; recall_level pilot.py:66-77 matches spells2.c:1153-1166)
- `town_stairs`: persisted file vs map memory (pilot.py:901-904,2131-2138)

## Contradictions and surprises
- **No contradiction with the brief's P1 note, but it is incomplete:** the 10 s inventory refresh is real, but it is the Pilot's cache of a client copy that is already current (c-tool.c:519-543, net-client.c:2006-2065). The `inven` query is local and cheap; a refresh before every use would cost little.
- `arrived_by='recall'` is documented (world.py:31) but never set.
- The map is polled in full (66x198, two string arrays) every 0.5 s or on every step (world.py:205-208; c-tool.c:545-602); per-step reads is how stale the map actually is.
- `monlist` is received but not used for decisions, though glyphs.py:18-20 calls it "the authority when they disagree".
