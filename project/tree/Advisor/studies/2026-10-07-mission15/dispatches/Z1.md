# Dispatch: Z1 zig-zag in corridors (mission 15)
- Brief: Reconstruct Dive04's corridor movement, explain it from mover.py/pilot.py, cost it, suggest a fix.
- Clerk run: 2026-10-07; sources: decisions.jsonl, events.jsonl (process 22:09:41, lines 111740-130996), pilot.log, mover.py, pilot.py (Explore, frontier), server cmd1.c run code, running memo. Scratch: scratch/z1_*.py|pkl.

## Answer
The user saw real diagonal lane-switching, not back-and-forth. Dive04 steps SW/NW alternately along a two-lane corridor, so the net travel is straight. It is also slow. Every step is a one-tile "run" (`custom . dir=1/7`) that ends after one step, so it costs a full walking turn (about 0.57 s) per tile instead of about 0.13 s. The cause is Explore's frontier goal: the nearest goal is always a diagonal tile in the other lane, so every path is 1 step long. That blocks stretch runs (_straight=1 < 3) and gives free runs only a diagonal direction. Cost: about 150 s (about 4.6% of the 54-minute mission, about 12% of dungeon moving time) in strict zig-zags alone.

## Suggested fix (INFERRED)
- **Goal choice:** when a frontier goal and a same-direction straight frontier both exist, or better, give the tile in the current lane (the tile directly ahead along the last step direction) priority: add a small extra cost (about 0.05) for any step whose direction differs from the previous step's, and a penalty (about 0.5) on goals that need a lateral move. Or pick as target the frontier tile that is farthest along the corridor axis rather than the nearest.
- **Mark the other lane explored:** treat floor tiles adjacent to our path as visited, so only the lane we're in yields a frontier.
- **Better:** when the last 2 explore plans were 1-step diagonals with alternating lateral sign, send a free run along the axis (the sign of the net displacement) instead of the diagonal.
- Keep the reversal check: the 1.1% reversals are separate.
- Verify first by logging `mem` rows around the Pilot in a zig-zag stretch (map snapshots are not logged).
