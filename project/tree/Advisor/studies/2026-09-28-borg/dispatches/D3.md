# Dispatch: Borg power, depth-readiness ("prepared"), and dive/gear rules
- Brief: D3 — how borg_prepared() gates depth, what happens when not prepared, how borg_power()
  scores gear, and what borg.txt/borg-formulas*.c configure, vs. our depth checkpoints.
- Clerk run: 2026-09-28; sources covered: borg-prepared.c (full), borg-power.c (full),
  borg-formulas.c (full), borg-formulas-calc.c (full), borg.txt (full, 1129 lines),
  borg-trait.c/.h (targeted sections for traits named below). Also opened, for context only
  (outside the assigned list, to interpret call sites): borg-flow-stairs.c, borg-caution.c,
  borg-think-dungeon.c, borg-think-dungeon-util.c.

## Answer
`borg_prepared(depth)` [SEEN borg-prepared.c:538-686] is a cascading gate: it walks up through
depth "milestones," and at each one checks concrete requirements (items, resists, HP, class/clevel
ratio, speed); the first unmet requirement returns a human-readable reason string, `NULL` means
"prepared." When not prepared, the borg does **not** stay and grind — the callers make it climb to
shallower depth or return to town/recall (never "wait it out"). `borg_power()` is a single scalar
that sums equipment power + inventory power + a **depth-readiness bonus** of 40000 points per
milestone depth already cleared, so gear that unlocks a deeper "prepared" depth is worth as much as
several basic resists at once. `borg.txt` ships a second, disabled-by-default implementation of both
systems as parsed formulas (a tiny expression language); the shipped formulas are a near-exact mirror
of the C thresholds, with a couple of arithmetic differences noted below. Against the brief's known
checkpoints: Free Action at dl20 matches; the Borg's "resist fire + 2 of 3 basics" actually applies
at dl21, all four basics by dl26 (looser than the "dl25" checkpoint by one level, tighter by nothing);
resist poison and confusion are gated at dl40, much looser than "1000 ft/dl20" and "before 1900 ft."

### 2. What the Borg does when not prepared — climb, recall, or stall; never "wait it out"
`borg_prepared()` is read by many decision sites; direct reading of the ones adjoining `borg-prepared.c`
[SEEN, though these files are outside the assigned list — read for interpretation]:
- **Won't take the down-stair**: `borg_flow_stair_more()` refuses to go down if
  `borg_prepared(depth+1) != NULL` (borg-flow-stairs.c:196-198) unless in lunal/munchkin mode or
  "brave." Likewise `borg.stair_more` is forced false the same way in `borg-caution.c:1146-1147` and
  `borg-think-dungeon.c:994-995,1864-1865`.
- **Climbs when not prepared for the current level**: `borg-think-dungeon-util.c:717-724,772-785` —
  if not prepared for *current* depth (`prep_cur_depth`), sets `g=-1` (go up), and if far out of
  depth (prepared only for ≤50% of max depth reached, and max depth>65) it instead sets
  `borg.goal.rising=true` to recall to town (:775-781).
- **"Power dive" when over-prepared**: if prepared even 5 levels deeper than current
  (`borg_prepared(cdepth+5)==NULL`) it dives immediately (:756-762,1897-1902 in borg-think-dungeon.c),
  and again at 75-99ft if prepared for the very next level (:764-769). This is the closest thing to a
  "dive rate": the borg doesn't crawl one level at a time when comfortably prepared, it skips ahead.
- **"Fear of depth"**: the only literal mention in the assigned files is a comment in
  `borg_prepared()`'s doc block — "we allow fear of one level up to and including the relevant depth"
  [borg-prepared.c:532-533] — the mechanism itself (a monster-danger "fear" flag) lives in
  borg-danger.c/borg-caution.c, out of this brief's scope.
- **Time-on-level / boredom**: `borg_time_to_stay_on_level()` [borg-think-dungeon-util.c:577-599]
  scales exploration time by clevel and level-feeling (50×clevel if clevel<10, else feeling-based);
  when that timer expires the borg picks a direction (up if `try_not_to_descend`, else 50/50 random)
  [:904-919]. This is a "boredom," not a `borg_prepared` check, but it interacts: if bored and unable
  to dive further (not prepared for depth+1) it climbs [:739-743].
- Recall into the dungeon on return to town is itself gated: only recalls back down if
  `borg_prepared(maxdepth*6/10)==NULL` (prepared for 60% of the deepest level reached) — otherwise it
  notes "Way too scary to recall down there!" and crawls down the stairs instead
  [borg-think-dungeon-util.c:671-713].
There is **no stair-scum-to-check-danger behavior** analogous to ours; the Borg's "lunal"/"self-lunal"
modes (config `borg_lunal_mode`/`borg_self_lunal`, default FALSE, documented borg.txt:258-289) are a
deliberate deep-diving stair-bounce for item farming while under-leveled, not a per-level safety check.

### 3. `borg_power()` — the master gear/purchase score
`int32_t borg_power(void)` [borg-power.c:1881-1912]: `= borg_power_equipment() + borg_power_inventory()
+ (levels_cleared_of_borg_prepared * 40000) + weapon_swap_value + armour_swap_value`, where
`levels_cleared` is found by scanning `borg_prepared(i)` from i=1 upward until it fails [:1898-1904].
This is used by "before/after" hill-climbing: e.g. `borg-item-wear.c:320,342` computes power before
and after tentatively wearing an item and keeps the change only if it increases. (Confirmed by
grepping call sites in borg-item-wear.c/store-buy.c/store-sell.c/borg-junk.c/borg-commands.c — file
names/line numbers only, not read in full; scope note below.)

Selected weights from `borg_power_equipment()` [borg-power.c:43-1117]:
- Weapon: damage×blows base term `dd*ds*20*(blows+1)` [:76,79]; to-hit ×100, to-dam ×30 [:82,85];
  slay/brand multipliers on top of a 2×/3×/5× base-damage term depending on slay tier (animal/evil
  2×; undead/demon/dragon/giant/brands 3×; *kill* flags 5×) [:99-156]; unidentified weapon/bow worn
  before clevel 15 & dl<10 gets a flat +1,000,000 / +6,000,000 "use it to ID it" bonus [:70-72,180-182].
- Speed: banded bonuses, e.g. +5 speed(115-119) ≈ +75,000-85,000; +10(120-124) ≈ +100,000-110,000;
  doubled scaling if `borg_worships_speed` [:245-303].
- Resists: flat per-flag bonus (fire 8000, poison 20000, conf 80000(!), all four basics together
  +10000 bonus) [:437-490], **plus** big one-time "Mega-Hack" bonuses of 100,000 each keyed to the
  depth milestones above once `MAXDEPTH+1` reaches that milestone (e.g. SINV/ESP@dl9, FA@dl19,
  RFIRE@dl24, all 4 basics@dl39 each, RCONF@dl45, Hold Life & +5 speed@dl45, RBLIND/ESP@dl54,
  RCHAOS@dl59, +20 speed Warrior@dl79) [:513-584]. Note the depth thresholds embedded here (`>=10`,
  `>=20`, `>=25`, `>=40`, `>=46`, `>=55`, `>=60`, `>=80` i.e. one-off-by-one from the `borg_prepared`
  gates, since these check `maxdepth+1 >= X` rather than `depth >= X`) are consistent with, but not
  identical in indexing to, the requirement table above.
- Armor: 2000-2500/point of AC below 15, tapering to 100-1500/point above 75 (worships_ac raises the
  taper) [:589-603].
- Curses/flaws: heavy penalties, e.g. -800,000 Aggravate/Siren, -700,000 no-teleport, -400,000 fear/
  drain-XP, -500,000 too-heavy weapon/bow, -9,999,999 "unknown curse" [:608-666].
- Activation items: a big per-activation-type bonus table (500-1000+ typical, up to 999,999 for "the
  One Ring" bizarre activation) [:702-1064].
Selected weights from `borg_power_inventory()` [borg-power.c:1122-1876]: fuel/food valued in
diminishing per-unit steps (60,000 → 6,000 → 200 per unit) [:1131-1150]; first Phase Door scroll alone
worth 50,000 [:1293-1294]; first WoR/first Recall items worth 50,000 each up to 3 [:1278-1279]; heals
and *heal* potions class-differentiated (Warriors value AHEAL more, 8000/unit vs 4000 for casters)
[:1350-1398]; carry-weight "encumbrance" penalty scales with how far over half-capacity the borg is
[:1868-1871].

### 4. `borg.txt` / `borg-formulas*.c` — a disabled, parallel configuration language
`borg_uses_dynamic_calcs = FALSE` by default [borg.txt:337], and the file itself documents why:
"Use the FORMULA SECTION below. If false the borg will use the calcs in the C code. Which is
recommended since those are honed more frequently than the dynamic calcs... Most borg users will have
more successful borgs by leaving this option as FALSE" [borg.txt:329-337]. So **the entire table above
is what actually runs**; borg.txt's `[BEGIN FORMULA SECTION]...[END FORMULA SECTION]` (lines 340-1129)
is an optional, hand-maintained mirror that a user could switch on.
- The formula language [borg-formulas.c, borg-formulas-calc.c]: three named sections — `Power`,
  `Depth Requirement`, `Restock Requirement` — each holding lines of `condition(...)`, `range(from,to)`,
  `value(type, name)`, `reward(...)` clauses, parsed into a token array and evaluated with a small
  precedence-aware expression evaluator supporting `+ - * / and or = < > <= >= !` [borg-formulas-calc.c:
  35-52,306-315,629-670]. `value(trait, X)` reads the same `borg.trait[]` array the C code uses;
  `value(config, X)` reads `borg_cfg[]`; `value(<tval>, name)` counts owned items by name.
- `Depth Requirement` section [borg.txt:990-1101] is close to a line-for-line mirror of
  `borg_prepared_aux()`: e.g. `depth(20): condition(!value(trait, free action));` [:1038] matches FA@dl20;
  `depth(21): condition(!value(trait, resist fire));` [:1040] confirms the dl21 (not dl25) reading
  above; `depth(40): condition(!value(trait, resist poison with swap));` [:1067] confirms dl40 for
  poison. It also explicitly uses **"...with swap"** trait names (see Contradictions/surprises).
- `Power` section [borg.txt:379-988] mirrors `borg_power_equipment/inventory` almost line-for-line,
  down to the same constants (e.g. `reward(1000000)` for the unID'd weapon, the same speed bands,
  the same 100,000-per-milestone "necessary flags" bonuses at the same maxdepth+1 thresholds) —
  cross-checked side by side for the sections read; no numeric mismatch found in the parts compared.
- Nothing else in borg.txt is a "dynamic formula" outside these three sections; the rest of the file
  (lines 1-339) is plain boolean/int config switches (worships_*, plays_risky, kills_uniques,
  no_deeper, lunal/self_lunal, munchkin_start, enchant_limit, etc.), not formulas.

### 5. Comparison with our checkpoints
- **Free Action & See Invisible by dl20 (1000ft)**: partially confirmed. Borg requires **Free Action
  at dl20** exactly [borg-prepared.c:271-272] — matches. But **See Invisible (or Detect-Invis or ESP)
  is required much earlier, by dl10 (500ft)** [borg-prepared.c:261-262], i.e. the Borg is *stricter*
  on SI than our dl20 checkpoint suggests, if "by 1000ft" was meant as the earliest requirement.
- **Four basic resists by dl25 (1250ft)**: close but not exact. Borg requires **Resist Fire + 2 of
  {acid,cold,elec}** starting dl21 (1050ft), and the **full four-basic set only by dl26 (1300ft)**
  [borg-prepared.c:281-360; borg.txt:1040-1060]. So the Borg is *stricter* by having a partial-resist
  gate one level early (dl21) but *looser* by one level (dl26 not dl25) for the complete set.
- **Resist poison by ~1000ft (dl20)**: contradicted. The Borg does not require Resist Poison until
  **dl40 (2000ft)** [borg-prepared.c:386-387; borg.txt:1067] — twice as deep as our checkpoint. The
  Borg is much *looser* here (it accepts poison risk for 20 levels that our rule would refuse).
- **Confusion/blindness resist before dl38 (1900ft)**: contradicted similarly. Borg gates Resist
  Confusion at **dl40 (2000ft)** [borg-prepared.c:388-389] and Resist Blind separately at **dl56
  (2800ft)** [borg-prepared.c:451-452] — both looser (later) than our "before 1900ft" rule, Blind
  especially so.

## Contradictions and surprises
1. The comment header "Essential Items for Level 25" [borg-prepared.c:278] is misleading — the gate
   it introduces is actually enforced starting at **dl21**, confirmed independently by the borg.txt
   mirror's explicit `depth(21)` tag [borg.txt:1040]. Anyone reading only the C comments (not the
   guard logic) would misdate this checkpoint by 4 levels.
2. `borg_prepared()`'s Free Action check reads the *bare* `BI_FRACT` trait [borg-prepared.c:271], but
   almost every other resist check in the same function reads the "SR"-prefixed trait
   (`BI_SRFIRE`, `BI_SRCOLD`, ...) which is `true` if the borg *currently has the resist, OR could get
   it from a swap item not worn, OR could cast Resistance with <15% fail* [borg-trait.c:2860-2905].
   So resists "count" even when not equipped, but Free Action must be equipped right now — an
   intentional asymmetry (FA needs to be active in the instant of danger; a resist can be swapped in
   proactively before a scary room).
3. The dynamic-formula system (borg-formulas.c) is a fully general expression engine — essentially a
   config-driven re-implementation of both `borg_prepared` and `borg_power` — but it is **off by
   default and the shipped docs recommend leaving it off** [borg.txt:329-337]. This means "what
   borg.txt configures" for depth rules and power weights is, in the shipped/default build, almost
   entirely inert; the live behavior is 100% hardcoded C.
4. `borg_power()`'s scan for `levels_cleared` (`for i=1..maxdepth+50: if borg_prepared(i) break`)
   [borg-power.c:1898-1904] means every gear decision folds in the *entire* depth-readiness table as
   a single additive term (40000/level) — a large single resist gap can cost the borg 40,000+ points
   of "power," larger than most individual item bonuses, which is presumably intentional (it makes
   the greedy hill-climb prioritize closing depth gates over marginal stat gains).

## Transfer notes
- The cascading milestone-gate pattern (`borg_prepared`) is a clean, portable idea: a small ordered
  list of (depth, requirement) pairs, first failure wins, human-readable reason returned. [INFERRED]
  This maps directly onto a Navigator `max_depth` policy and would be easy to reproduce for our
  Warrior (no swap items, no spells — so we'd only ever use the "bare" trait, never the "SR" variant).
- The "climb when not prepared for depth+1, power-dive when prepared 5 levels ahead" logic assumes the
  bot can freely choose to explore up or down at will between turns; it has no real-time cost model.
  [INFERRED] For us (real-time, connected stairs, stair-scum dive), the analogous move is simpler:
  gate `max_depth` directly from the requirement table, and dive via stair-scum rather than "walking
  to stairs then deciding."
  `borg_power()`'s single hill-climbing scalar for gear decisions is attractive but heavyweight (nearly
  2000 lines of hand-tuned weights); for a throwaway Warrior with no spellcasting and few resist
  sources, a much smaller subset (weapon damage, AC, a few resist flags, speed, FA, light) would
  likely capture most of the value. [INFERRED]
- The dynamic-formula config language is a good design reference if the Advisor ever wants the
  Navigator's depth/power rules to be data-driven rather than hardcoded, but note the Angband
  authors' own experience: they built it and then recommend leaving it off in favor of hand-tuned
  code — a caution against over-investing in configurability. [REPORTED, borg.txt:329-337]
