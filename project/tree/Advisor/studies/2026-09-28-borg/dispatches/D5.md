- Brief: D5 — swap items, wearing/ID logic, consumable quotas, shopping, junk, failure-prone parts
- Clerk run: 2026-09-28; sources covered: borg-trait-swap.c (1300 ln, full), borg-item-wear.c (1578
  ln, full), borg-junk.c (1370 ln, full), borg-store-buy.c (1257 ln, full), borg-store-sell.c (1288
  ln, full), borg-home-notice.c (951 ln, full), borg-home-power.c (547 ln, full), borg-item-use.c
  (1263 ln, full); plus a targeted read of borg-prepared.c (out of the named list — see note under
  Q3) and one-line greps into borg-caution.c, borg-trait.c, borg-init.c, borg-flow.c, borg-think-store.c
  to trace where swap/quota values are actually used.

## Answer
Swap gear is only *identified*, never *worn*, by borg-trait-swap.c; it is worn defensively by
`borg_backup_swap()` in borg-item-wear.c, triggered when local danger exceeds `avoidance/3`.
General re-gearing is power-comparison driven (`borg_power()`/`borg_danger()` deltas), with a
brute-force "best possible wardrobe" search done only at home. Consumable "quotas" are gating
thresholds baked into per-depth-band `if` chains in `borg-prepared.c` (not in the 8 named files),
used both to decide readiness to dive deeper and to trigger a return to town. Shopping is a
power-maximizing loop (buy if it raises `borg_power()`/`borg_power_home()`, sell if removing it
doesn't lower it) with several loop-prevention hacks. Junk logic is depth- and danger-gated
power-preserving drop/consume routines. The code base is full of explicit "anti-loop"/"anti-bounce"
comments admitting known item-letter/slot staleness bugs — directly relevant to the Pilot's bug.

## Findings

### 1. Swap items — borg-trait-swap.c
1. Two functions only *notice* (identify) swap candidates; they don't equip anything.
   `borg_notice_weapon_swap()` (borg-trait-swap.c:158-742) scans the pack for `TV_HAFTED/POLEARM/
   SWORD/DIGGING`; `borg_notice_armour_swap()` (borg-trait-swap.c:747-1298) scans wearable armour
   types (RING/AMULET/BOOTS/HELM/CROWN/SHIELD/CLOAK/SOFT_ARMOR/HARD_ARMOR/DRAG_ARMOR). [SEEN]
2. Swaps are only carried once `BI_MAXDEPTH >= 50`, except diggers which are kept regardless of
   depth (borg-trait-swap.c:193-196: "Don't carry swaps until dlevel 50. They are heavy. Unless the
   item is a digger"). Armour-swap noticing has the same depth-50 gate at line 786-787. [SEEN]
3. Swaps are globally disabled below dungeon level 90 or by config: `borg_uses_swaps()` returns
   `borg_cfg[BORG_USES_SWAPS] && borg.trait[BI_MAXDEPTH] < 90` (borg-trait.c:1025-1028); the option
   is `borg_uses_swaps` in borg.txt (borg-init.c:70). [SEEN]
4. Value formula (`v`) rewards raw damage (`dd*ds*25` weapon / `dd*ds*35` armour) times blows,
   to-hit/to-dam bonuses, slays/brands the borg currently lacks (half value, doubled to full if the
   borg also lacks the broader "slay evil" for orc/troll), and resists/immunities with fixed point
   values, e.g. resist poison +20000, free action +10000, see-invisible +50000, immune fire +70000,
   +10000 bonus for having all four basic resists together (borg-trait-swap.c:474-509,1045-1080).
   "Bad" curse (any of a fixed list, borg-trait-swap.c:138-153) is a flat -100000 penalty; needing
   decurse is -5000; aggravate is -8000. Items valued ≤1000 are discarded (line 543-544). [SEEN]
5. Special-case bonuses: +90000 for cold/fire immunity if Tarrasque is alive and depth≥75
   (borg-trait-swap.c:511-522, 1079-1090, checked via `borg_race_death[borg.mon.tarrasque]==0`);
   +100000-105000 "mega-hack" bonuses for resist nether/chaos/disenchantment once
   `MAXDEPTH+1 >= 55/60`, with an explicit check that the *other* swap slot doesn't already cover
   the same resist (line 530-538, 1092-1107). [SEEN]
6. After picking the best candidate, the code separately computes how many enchant points the swap
   "needs" (`enchant_weapon_swap_to_h/to_d`, `enchant_armour_swap_to_a`), targeting +10 if an
   Enchant spell/scroll is available at ≤65% fail, else +8 (borg-trait-swap.c:622-643, 1286-1297).
   [SEEN]
7. Swap-in-during-danger: `borg_backup_swap(int p)` (borg-item-wear.c:534-728), called only from
   borg-caution.c:1025-1031 when `pos_danger > borg.avoidance/3`. It simulates wearing `armour_swap`
   and/or `weapon_swap`, recomputes `borg_danger()`, and **vetoes** the swap (forces danger=9999) if
   it would strip a currently-held resist-conf/resist-blind/free-action the character needs
   (borg-item-wear.c:613-621, 672-681), or if the swap is an un-*ID*'d randart or still cursed
   (628-633, 693-699). It then requires the resulting danger to be low enough — `≤ avoidance*2/3` if
   a unique is nearby, else `≤ avoidance/2` (borg-item-wear.c:712-714) — and strictly lower than the
   current danger `p`, before actually wearing it. [SEEN]
8. Swap items are protected everywhere else: never crushed as junk (borg-junk.c:279-282, 561-565,
   1014-1018), never sold (borg-store-sell.c:333-336, 997-1001, 1206-1209), and there is a dedicated
   "buy a better swap from home" path (borg-store-buy.c Steps 7A/7B, lines 953-1174) that compares
   against `weapon_swap_value`/`armour_swap_value` directly rather than full `borg_power()`. [SEEN]

### 2. Wearing — borg-item-wear.c
1. `borg_wear_stuff()` (borg-item-wear.c:745-1037) is the general "wear anything better" loop: for
   each aware, valued, not-recently-worn item it simulates wearing it (memcpy into the slot,
   `borg_notice(true)`, `borg_power()`, and `borg_danger()`), and only accepts it if simulated
   danger does **not** increase (line 907) and power beats the current best by more than 50 (line
   912-914 — "essentially equal" swaps rejected to avoid churn). Ring slots get an extra
   1%-per-tick random re-check (`randint0(100)==10`, line 921) or are forced for the One Ring. [SEEN]
2. Unknown/cursed handling: items are skipped from `borg_wear_stuff()`'s scan only if they are
   un-*ID*'d random artifacts under `birth_randarts` (line 805-806); ordinary cursed items are not
   filtered there — the curse's effect is assumed to show up in the simulated `borg_power()`/
   `borg_danger()`. The wardrobe-optimizer `borg_best_stuff_aux()` and `borg_backup_swap()` do
   explicitly skip `cursed && !uncursable` items (borg-item-wear.c:1276, 632-633, 698-699). [SEEN]
3. ID priority: `borg_test_stuff()` (borg-item-wear.c:84-245) ranks items to identify by
   `item->value + 150000` for artifacts, `+100000` for ego items with a random power, `+20000` for
   items flagged `needs_ident`, plus a `BI_MAXDEPTH`-scaled reward for un-aware wearables/wands/
   potions/food (so deeper finds get IDed sooner). It refuses to ID while `borg_danger(...) > 1`
   (no IDing in a fight) and requires ≥50 spent SP be recoverable before spending a spell ID
   (line 89-98). [SEEN]
4. Ring management is a deliberate two-step dance: `borg_swap_rings()` (259-379) may strip the
   "tight" (right) ring if the world without it scores no worse (`v2>v1`), then
   `borg_wear_rings()` (397-520) re-fills the empty right slot with whichever ring in the pack gives
   the best simulated power — this is how the borg keeps its single "protected" ring slot occupied
   by the best ring even as new rings are found. [SEEN]
5. `borg_best_stuff()`/`borg_best_stuff_aux()` (borg-item-wear.c:1335-1435, 1212-1325) is a full
   recursive brute-force search over every equipment slot, trying every pack **and home** item in
   that slot, run only while at home (`shop_num == BORG_HOME`, line 1347). Results are cached as
   tval/sval/pval triples in `borg.goal.best_item` (not raw slot indices, because slots shift) and
   executed one change at a time by `borg_one_step_wearing_best()` (1077-1207), which explicitly
   re-locates each target item by tval/sval/pval every step "because they could have moved slots
   since other objects are being taken off and dropped into inventory and the home"
   (borg-item-wear.c:1135-1137, comment). [SEEN]

### 3. Consumable quotas
Not present in the eight named files — `borg-item-use.c` only issues quaff/read/eat/zap actions
and has no notion of a desired quantity. The quota/threshold table lives in **borg-prepared.c**
(`borg_prepared_aux()`, `borg_restock()`, `borg_must_return_to_town()`), a file not in the brief's
source list; I read it because it is the only place in the codebase where "how many of X to carry"
numbers with depth/clevel gates actually exist, and the brief explicitly asks for this table. Flag
this as a scope extension. [SEEN, but out-of-brief file]

### 4. Shopping — borg-store-buy.c / borg-store-sell.c / borg-home-*.c
1. `borg_good_buy()` (borg-store-buy.c:68-217) is the buy filter: no enchanted/costly ammo below
   clevel 35; correct spellbook class only; Black Market (`who==6`) is blocked below gold/clevel
   thresholds (20000g@<15clevel, 15000g@<35clevel, 10000g floor) except for a fixed allow-list
   (Remove Curse scroll if first-cursed, Life/Healing potions, class-relevant rods, dungeon
   spellbooks, Teleport/Teleport Level scrolls) — buying one of those can also trigger
   **money-scumming**: `BORG_MONEY_SCUM_AMOUNT` is set if clevel≥10, has light, food+num_food≥100,
   item cost≤85000, and `adj_dex_safe+clevel > 90` ("good chance to thwart mugging")
   (borg-store-buy.c:140-160). [SEEN]
2. Buy priority is staged: Step3 buy-useful-from-shop (222-440, requires strictly higher
   `borg_power()` or a cheaper tie), Step4 buy-useful-from-home (445-710, same power test,
   special-cased for both ring slots), Step5 grab-interesting-for-home-stockpile (715-851, requires
   clevel≥15, Sauron not yet dead, and that it beats an *empty* home's power before even trying),
   Step6 grab-useless-from-home-to-sell (856-948), Steps 7A/7B buy-swap-weapon/armour-from-home
   (953-1174, compares against swap value only). [SEEN]
3. Selling: `borg_store_buys()` (borg-store-sell.c:701-811) hard-codes which shop buys which tval
   (General=food/ammo/diggers, Armoury=armour, Weaponsmith=weapons/ammo, Bookstore=own-class books,
   Alchemist=potions/scrolls, Magic Shop=rings/amulets/wands/staves/rods, Black Market=anything if
   `birth_no_selling`). `borg_good_sell()` (816-941) additionally refuses to sell unidentified
   valuable items unless there's a duplicate to spare, refuses items just bought back (loop guard),
   and gates several types behind "known" status unless deep (`MAXDEPTH>=35`) or worshipping gold /
   money-scumming / clevel<10. `borg_think_shop_sell_useless()` (946-1082) sells only if the
   resulting `borg_power()` doesn't drop, preferring the cheapest of equal-power sales first (line
   1050-1053) "because we may have to buy the item back". [SEEN]
4. Home valuation: `borg_power_home()` = `borg_power_home_aux1()` (equipment-like flags/resists,
   borg-home-power.c:33-352) + `borg_power_home_aux2()` (consumable stockpiles, 359-528). Both use
   diminishing/capped rewards — e.g. resist acid is worth +1000 for 1, +1500 for 2, then only +1/each
   further copy (home-power.c:102-107); duplicate items above type-specific caps are penalized
   (`num_weapons>5` costs 2000/extra, `num_duplicate_items` costs a flat 50000/item, home-power.c:312-348).
   The home essentially wants "2 of each resist/special power for redundancy" plus depth/clevel-gated
   stockpiles of food, ID scrolls, enchant scrolls, escape/teleport/recall items, and healing
   potions (home-power.c:365-528), each with its own cap (e.g. escape capped at 85, teleport-staff
   stacks capped at `kb_info[TV_STAFF].max_stack` beyond which each extra costs -50000). [SEEN]
5. `borg_notice_home()`/`borg_notice_home_aux()` (borg-home-notice.c:343-932) recomputes all the
   `num_*`/`home_stat_add[]` counters used by aux1/aux2 by scanning home wares + worn equipment +
   known player-race flags + currently-legal spells (e.g. knowing Remove Hunger adds 1000 "food",
   knowing Identify Rune adds 1000 "ident" — spells are treated as infinite consumable supply,
   borg-home-notice.c:797-838). `borg_think_home_sell_best()` (borg-store-sell.c:398-524) brute-force
   tries substituting each pack item into each home slot one at a time, keeping whichever single
   substitution raises `borg_power_home()` most — this is the mechanism actually used by Steps 1/5/6
   above. [SEEN]

### 5. Junk — borg-junk.c
1. `borg_destroy_floor()` (45-70) auto-destroys any floor item the borg itself flagged as trash
   (sentinel `take->value == -10`) via `k`-`-`-`a`-`a`. [SEEN]
2. `borg_consume()` (75-244) destroys junk *by using it* — a fixed allow-list of potions (CLW/CSW/
   CCW/Healing/Star-Healing/Life/Restore-Mana/Heroism/Berserk/Resist-Heat/Resist-Cold/Infravision/
   Detect-Invis/Cure-Poison/Speed/Inc-Exp, plus gain-stat potions gated by class and "not already
   maxed at 118"), scrolls (Light/Monster-Confusion/Trap-Door-Destruction/Satisfy-Hunger/Dispel-
   Undead/Blessing/Holy-Chant/Holy-Prayer), food/mushrooms. [SEEN]
3. `borg_drop_junk()` (249-492) only runs if a `borg_do_crush_junk` flag is set and danger ≤
   `CURHP/10`. "Junk" value threshold to *keep* an item **rises with depth**: keep anything of value
   at `CDEPTH<5`; value>15 discarded below dlvl10; >100 kept below dlvl15; >500 below dlvl30; >1000
   below dlvl40; >1200 below dlvl60; >1400 below dlvl80; >1600 below dlvl90; >4800 below dlvl95;
   >5600 below dlvl127 (borg-junk.c:393-422) — i.e. the deeper the borg is, the pickier it is about
   what counts as junk (higher floor). Stat-boosting items get +2000 value; current ammo type +5000;
   several "cool" consumables (Healing/Life/Speed potions, drain-life/annihilation wands, dispel-evil
   /power/holiness staves, teleport-away wand for warriors, un-exhausted teleport-level scrolls,
   ego items with a random power) get +5000 (borg-junk.c:323-369). Diggers and off-class ammo are
   always worthless (value=0). Below clevel≤20 (or if `BORG_WORSHIPS_GOLD`/money-scumming), almost
   nothing is junked so it can be sold in town instead (385-391). [SEEN]
4. `borg_drop_hole()` (515-950) only fires when the last pack slot is full and only on a floor tile;
   danger gate is `≤ CURHP/10` (or `≤ 2*CURHP/3` if not at full HP, line 534-541). Two passes: a
   conservative pass that protects unidentified boots (could be Speed), a currently-wielded digger's
   displaced weapon, un-*ID*'d egos/artifacts, and several "cool" consumables; then a `desperate`
   recursive second pass (line 946-947) that allows crushing all of those but with large value
   boosts (5000-10000) so the *least bad* one is still chosen. Above clevel 35, per-tval multipliers
   heavily protect rings/wands/rods/staves (×5-×10 or flat 300000) versus scrolls/potions (crushed
   more freely, borg-junk.c:696-793). [SEEN]
5. `borg_drop_slow()` (960-1146) only fires when `BI_SPEED<110` (never in town, never in "munchkin
   mode"), trading a gold-based "greed" (clamped 0-25000, reduced by slowness) against weight
   (`weight*100` reward) — literally drops heavy junk to regain speed. [SEEN]
6. `borg_dump_quiver()` (1155-1248) dumps ammo not matching the wielded launcher's tval or with
   negative to-h/to-d, and caps missiles at `quiver_capacity = (max_stack-1) * mult * quiver_size`
   where `mult=2` for Warrior/Ranger, else 1 (line 1180-1187). [SEEN]
7. `borg_remove_stuff()` (1260-1368) takes off any worn item whose removal does not lower
   `borg_power()` — a generic "am I wearing something actively bad" cleanup. [SEEN]

### 6. Failure-prone parts / TODOs
1. Every routine above (`borg_wear_stuff`, `borg_backup_swap`, `borg_swap_rings`,
   `borg_best_stuff`, buy/sell steps, junk drops) works by: memcpy an item into a slot, call
   `borg_notice()`/`borg_power()`/`borg_danger()`, memcpy the item back, then only *afterward* issue
   the real keypress addressed by a **pack-slot letter** (`all_letters_nohjkl[i]`). This assumes the
   world (and the pack's slot order) is unchanged between the simulation and the keypress. [INFERRED
   from the code pattern repeated in every function cited above]
2. The codebase's own comments admit this breaks: borg-item-wear.c:1135-1137 says items acted on by
   `borg_one_step_wearing_best()` must be **re-located by tval/sval/pval, not by stored slot index**,
   "because they could have moved slots since other objects are being taken off and dropped into
   inventory and the home." [SEEN — direct comment]
3. `borg-junk.c:1162-1165` explicitly names a known bug class: "Prevents swap loops when hungry or
   weak. This is a workaround for a deeper bug where the Borg may swap items back and forth due to
   power calculation issues and ultimately die from hunger." Comparable "prevent the swap till you
   drop loop" comments appear at borg-item-wear.c:424, 553, 769, guarded by `borg.antibounce_count`
   thresholds (150/300/1300) and `borg_timer(borg.time.level) > 1000/2000` "sitting on level
   forever" checks. This is the vanilla Angband analogue of the Pilot's item-letter bug: the Borg's
   own authors hit repeated wrong-item/oscillation failures and patched them with counters rather
   than fixing the root cause. [SEEN]
4. Two open TODO/FIX markers: borg-home-notice.c:144 "!FIX This needs to change into an array like

## Contradictions and surprises
- The brief's phrasing ("how it swaps in during danger") implies swap items are a general-purpose
  danger response; in fact only one narrow function (`borg_backup_swap`) ever equips them, gated at
  `avoidance/3`, and it can be completely disabled by `BI_MAXDEPTH >= 90` or `borg_uses_swaps()`
  false — deep-game the mechanism silently turns off. Worth flagging since our diving depths
  (0-1500ft / dlvl 0-30) never reach 90, so this cutoff is irrelevant to us either way. [SEEN]
- Consumable "quotas" are not a single table anywhere; they are duplicated almost verbatim in two
  places (`borg_prepared_aux` for "may I descend" and `borg_restock` for "must I go up"), with
  slightly different depth breakpoints and thresholds each time (e.g. CCW+CSW+ACLW combined ≥2 to
  descend past dlvl4 vs ≥1 to avoid restocking at dlvl6-9). This duplication is itself a
  maintenance smell worth noting for our own design (keep depth-gates in one table, not two).
- This file lived outside the brief's named source list (borg-prepared.c). I read it because
  borg-item-use.c, the file named for "how it addresses items," contains no quota logic at all —
  the brief's Q3 cannot be answered from the 8 named files alone.
