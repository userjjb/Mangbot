# Dispatch: D1 code audit of the drop model (objgen.py, build_drops.py, build_jewellery.py vs the 1.5 C source)
- Brief: audit every generation/value mechanic of the Advisor's drop model against object2.c, xtra2.c, store.c, z-rand.c and the lib/edit data; list discrepancies with effect sizes; check the docstring edge cases; say what shops pay on.
- Clerk run: 2026-10-23; sources covered: object2.c (437-800, 1075-1420, 1941-1981, 2027-3930), xtra2.c (1925-2290), store.c (127-260, 660-700, 1325-1400, 1972-2210), z-rand.c, z-rand.h, init1.c/init2.c alloc code, mdefines.h, melee2.c 3140-3235, monster2.c 1057-1160, object.txt, ego_item.txt (parsed whole), artifact.txt (parsed whole), monster.txt (via model parser), the three model files. Scratch scripts: `scratch/D1/`.

## Answer
The model matches the C code on every mechanic I could check. The only quantitative deviation is `m_bonus`, which uses a rounded Gaussian instead of the real `randnor`. That overstates the expected value by 0-4%, which is negligible. Three things the model leaves out can matter:
- Drops lost for lack of clean floor (small to medium, depends on terrain).
- **Shops pay on the known-to-player value, not `object_value_real`.** An unidentified weapon or armour piece sells at the kind's base cost only. This is big for the realisable value of plus/ego gear.
- Carried objects (TAKE_ITEM) and DROP_CHOSEN do not matter for a 0-1500 ft character.

I found no error in drop count, gold/item split, object level, gold piles, the power roll, the `get_obj_num` pick, the artifact gates, the ego pick, or the stack sizes.

## Findings
1. **Drop count and gold/item split** match [SEEN] (xtra2.c:2028-2033, 2062-2065). DROP_60/90 are `randint0(100) < 60/90`, and the dice flags use `damroll(n,2)`. Gold is placed if `do_gold && (!do_item || randint0(100)<50)`, with `do_gold = !ONLY_ITEM` and `do_item = !ONLY_GOLD`. DROP_GOOD does not change the 50% gold chance. Model: build_drops.py:185-196 (`count_dist`) and :211-218 (`pg`).
2. **Object level** is `(Depth + r_ptr->level)/2` (xtra2.c:2062), reset to `Depth` afterwards. Model: `L=(D+level)//2` (build_drops.py:213) [SEEN]. The artifact rolls get the real dungeon depth (object2.c:3651, 3686), and the model passes `D` to them (build_drops.py:126, 140-141) [SEEN].
3. **Allocation table and `get_obj_num`** match [SEEN] (object2.c:624-737; init2.c:1888 `p = 100/chance`; GREAT_OBJ=20 in mdefines.h:172; MAX_DEPTH=128 in defines.h:162).
   - 1-in-20 boost: `1 + level*128/randint1(128)`.
   - 1 pick 40%, 2 picks 50%, 3 picks 10%, keeping the higher alloc level.
   - No `A:` entry in object.txt has rarity 0 (grep), so the model's `if rar:` skip loses nothing. All 17 INSTA_ART kinds have no `A:` line, so they are never rolled directly.
   - I ran an independent simulation of the C algorithm (scratch/D1/pick.py, 60,000 draws at L=20 normal and L=35 good). Total-variation distance to `pick_dist` was 0.024 and 0.016, below the sampling-noise floor.
4. **place_object** matches [SEEN] (object2.c:3641-3694).
   - `prob = good ? 10 : 1000` and `base = good ? object_level+10 : object_level`.
   - `kind_is_good` is applied only for DROP_GOOD/GREAT (kind_is_good at 3466-3528).
   - `apply_magic(Depth,&forge,object_level,TRUE,good,great)` runs on the kind chosen from L+10, so DROP_GOOD uses `get_obj_num(L+10)` and `apply_magic(L)` as the model assumes.
   - `make_artifact_special` is tried first, and the normal path runs only if it fails. The model's `(1-ps)*normal + ps*special` is equivalent.
   - The model's `kind_is_good` (objgen.py:98-111) matches the C kind_is_good, including SV_BOOK_MIN_GOOD=4, SV_AMMO_MAGIC=4 excluded, and the Ring of Speed (sval 31, the only tval-45 kind named "Speed").
5. **Power roll** matches [SEEN] (object2.c:3207-3234). `f1=min(L+10,75)`, `f2=min(f1/2,20)`. `good||magik(f1)` gives power 1, and `great||magik(f2)` gives power 2. Otherwise `magik(f1)` gives -1, and `magik(f2)` gives -2. Model: objgen.py:152.
6. **Artifact rolls** match [SEEN] (object2.c:3242-3253 and 2205-2250).
   - `rolls=1` if power>=2, `rolls=4` if `great`, and 0 if an artifact already exists.
   - `make_artifact` loops over a_info[16..] with the same tval/sval and rolls an out-of-depth gate of `1/((level-Depth)*2)` when `level>Depth`, then rarity `1/rarity`. The first artifact to succeed wins.
   - The player-already-found check (`a_info[i] > cfg_preserve_artifacts`, cfg PRESERVE_ARTIFACTS=3) is not modelled. It only removes artifacts, and the model excludes them from `e_value` anyway.
7. **Special artifacts** [SEEN] (object2.c:2124-2200).
   - The loop covers i=0..15 (ART_MIN_NORMAL=16, mdefines.h:1974). Gates: min-depth `1/((level-Depth)*2)`, rarity `1/rarity`, then base-kind level versus `object_level` with `1/((klevel-object_level)*5)`.
   - The "Depth > level+20" branch computes `d = (level-Depth)*2 < 0`. `randint0(m)` is `Rand_div`, which returns 0 for `m <= 1` (z-rand.c:162), so `randint0(d) != 0` is false. The branch never skips, and **there is no upper-depth cutoff**. The model has none either (objgen.py:260-272), so it is correct. K1 says the same.
   - `randint1(m)` is `randint0(m)+1`, so `randint1(negative)=1`.
8. **Stacks and artifact base kinds** [SEEN].
   - `number=damroll(6,7)` (mean 24) is set after `apply_magic`, only for TV_SPIKE, SHOT, ARROW and BOLT, and not for artifacts (object2.c:3688-3694). `invcopy` sets number=1 (1959). No other `number =` in object2.c applies at creation.
   - `make_artifact` runs while number is still 1, so its `number != 1` check (2214) never blocks. It cannot hit ammo anyway: artifact.txt has no ammo, and the normal-artifact tvals are 19, 20, 21, 22, 23 and 30-38.
   - The brief's "already known" items hold. Normal artifacts (index 16+) are all weapons and armour (tvals 19-23, 30-38). Specials 1-15 are lights 39 (Galadriel, Elendil, Thrain, Westernesse), amulets 40 and rings 45. The only cost-0 artifact is Camlost (58).
   - Model STACK={5,16,17,18} is right (build_drops.py:38).
9. **a_m_aux_1/2 and ego pick** match [SEEN] (object2.c:2381-2423, 2429-2680).
   - To-hit/dam/AC use `randint1(5)+m_bonus(5)`, plus `m_bonus(10)` at |power|=2.
   - Digger pval is `-(5+randint1(5))` at power -2 and `-pval` at -1.
   - Extra dice at power 2 apply to hafted/polearm/sword and ammo, but not to bows or diggers. The loop is `randint0(10*dd*ds)==0`, capped at 9.
   - Dragon armour never gets an ego (a_m_aux_2 returns early), but it does get to-AC plusses. Armour at power 0 gets nothing.
   - Ego pick: `randint0(e_max=136)` for up to 999 tries, accepting on `level<=ego level`, `randint0(rarity)==0`, tval/sval range, and the curse rule (power>1 excludes curse egos, power<-1 requires them). This is equivalent to weight 1/rarity. I checked all 118 egos in ego_item.txt against `K1_egos.csv`: no differences. (Shattered) and (Blasted) have no `T:` lines, so they never match, and the model's `if not slots: continue` drops them correctly.
10. **Ego bonuses** [SEEN] (object2.c:3405-3440). Curse or broken egos subtract `randint1(max)`, other egos add `randint1(max)`. All `C:` maxima in ego_item.txt are non-negative, so the model's `r1()` negative-n branch is never used. Morgul is the only curse ego with cost>0 (1). Its value is still 0 because power -2 plusses are negative.
11. **object_value_real** matches [SEEN] (object2.c:1136-1345).
    - It uses total to_h+to_d+to_a ×100 for armour and weapons (armour counts to_h and to_d too), and ammo to_h+to_d ×5.
    - Negative pval returns 0, as do weapons with to_h+to_d<0 and armour with to_a<0. Extra dice need `ds` equal to the kind's.
    - Pval credits are STR..CHR 200, STEALTH/SEARCH 100, INFRA/TUNNEL 50, BLOWS 2000, and SPEED ×100000 (ring ×50000, amulet ×25000).
    - Artifacts use `a_ptr->cost`, and egos add `e_ptr->cost`.
    - Random xtra sustains/resists/powers go only into f2/f3 (object1.c:1017-1031), so they add no value.
    - All 12 pval flags are covered by objgen.PVAL_COST. The model's jewellery FLAGCOST omits BLOWS, but no ring or amulet kind has it (checked against each RULES kind's flags).
12. **Jewellery** rules (a_m_aux_3, object2.c:2675-3088) match every RULES line in build_jewellery.py [SEEN], including Speed (`randint1(5)+m_bonus(5)` plus a 50% geometric increment), amulet of Speed `randint1(randint1(3))`, Trickery `1+m_bonus(3)`, and the cursable/not-cursable split. Power 0 becomes -1 with probability 50% only for TV_RING and TV_AMULET (object2.c:3350). The model applies this in build_drops.py:132 and build_jewellery.py (`power==0` branch).
    - Kinds without a case in C (resists, sustains, FA, SI) keep their kind cost.
    - The 9 always-cursed kinds all have cost 0, so `object_value_real` is 0 for them.
13. **place_gold** matches [SEEN] (object2.c:3860-3915). `i=(randint1(L+2)+2)/2-1`, plus `randint1(L+1)` with 1/20, capped at 17; `coin_type` overrides it. `pval = base + 8*randint1(base) + randint1(8)`, with mean `5*base+8.5`. Gold costs run from copper 3 (object.txt:3849-3852) to adamantite 80 (3934-3937), and kind index 480+i is the i-th gold kind. `get_coin_type` (xtra2.c:1938-1960) matches the model's `coin_type`. Only the five creeping-coin races have symbol `$`.
14. **Shops pay on the known-to-player value** [SEEN]. `sell_haggle` computes the offer through `price_item` -> `object_value(p_ptr, o_ptr)` (store.c:192, 1345-1346), before the item is identified. `object_value` returns `object_value_real` (0 if cursed or broken) only if `object_known_p` (ID_KNOWN, or EASY_KNOW and aware; mdefines.h:2676). Otherwise it uses `object_value_base`, which for an aware flavourless kind (all weapons and armour) is just `k_ptr->cost` (object2.c:1075-1112). Unaware potions are 20, scrolls 20, staffs 70, wands 50, rods 90, rings 45 and amulets 45. The item is only made known after the sale (store.c:2147-2173, `object_known`), and the true value is used only for the owner's comment text. The offer is `value * min(100, 100+300-(greed+factor))%` (÷3 in the black market), capped at the owner's `max_cost` (store.c:1352-1366). `store_will_buy` refuses items whose `object_value` is <=0.
    - Rough measure (scratch/D1/kc.py): the expected kind-cost-only value of one generated object is 92, 146, 352, 675 and 892 at L=5, 10, 20, 30 and 40. The model's `e_value` is 164, 240, 524, 910 and 1195. For DROP_GOOD it is 243, 268, 377, 785 and 1710 versus 1305, 1577, 1971, 2600 and 3516. So an unidentified sale realises about 55-75% of the model's value for normal drops and about 12-50% for good drops.

Not discrepancies, but checked: unaware flavour items in `e_value` use the kind cost, which is correct for a known item; wand/staff charges use mean charges, which is exact in expectation because the formula is linear in pval (`value/20` is an integer multiple of pval; the Magic Missile model value of 315 matches).

## Contradictions and surprises
- build_drops.py's docstring says values are "what a shop's price is based on". That holds only for identified items (finding 14). Nothing in the brief's "already known" list was contradicted.
- Surprise: the "Depth > level+20" max-depth gate in `make_artifact_special` is dead code, because of the negative-`d` / `randint0(m<=1)=0` behaviour (finding 7).
- Surprise: object2.c:2205 onwards contains leftover `printf("Out of depth?")` and `printf("Art rarity roll...")` debug lines in `make_artifact`, so the server writes to stdout on every artifact roll. This is harmless to generation.

## Leads
- Realised value depends on identification before sale. Check how the Pilot IDs items (Identify scroll, ID-by-use, rune ID). Pseudo-ID was out of scope for this dispatch.
- Check data/drops/drop_sim.py to see whether the floor-space loss is large enough to scale `e_drops` for multi-drop monsters (4D2 and similar).
- The `e_value_cap` of 25,000 versus owner purses (25,000-150,000) is a model choice, not a code fact. I did not check the purse values.
- spells2.c:2684 (noted in K1): an `apply_magic(127,...,TRUE,TRUE,TRUE)` effect that is not part of drops.
