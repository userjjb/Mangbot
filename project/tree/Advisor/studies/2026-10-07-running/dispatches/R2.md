# Dispatch: server pathfinding and what a human client sends
- Brief: R2 pass 1 - server/pathfind.c, human client run/travel keys and packets, why the Pilot dropped server pathfind, per-player run/disturb options.
- Clerk run: 2026-10-07; sources: github/src/server/{pathfind.c,cmd1.c,cmd2.c,net-game.c,cave.c,dungeon.c,tables.c,xtra2.c}, client/{c-cmd.c,c-cmd0.c,c-util.c,c-tool.c,net-client.c}, common/{pack.h,defines.h}, git 512f394/649b3d4/d682520/468b717, project notes.

## Answer
Server pathfind (PKT_PATHFIND, 2 bytes Y X) is a flood-fill over a 50x50 window (+-25 tiles, max path 250) that treats never-seen grids as open. It then replays the path as a "run": one step per game turn at run speed, cancelled by disturb(). A human client sends PKT_RUN for shift+dir / '.'+dir. The only client route to PKT_PATHFIND is a mouse left-click on the map. Keyboard travel only exists as 'g' inside the server's look/target mode. The Pilot dropped it because unseen edge squares count as open (it walked off the level, 2S -> 3S). It is fixable on the Pilot side, and it could also be used in the dungeon, but see item 3.

## Findings
1. Algorithm. `findpath()` (pathfind.c:80-217): a naive repeated relaxation (BFS-like, 8 directions, all steps cost 1) over `terrain[MAX_PF_RADIUS][MAX_PF_RADIUS]`. MAX_PF_RADIUS=50, MAX_PF_LENGTH=250 (common/defines.h:883,886). The window is px-25..px+24 and py-25..py+24 (pathfind.c:60-64). A target outside the window gets `bell()` and returns FALSE, so there is no path and no error is sent (:91-112). [SEEN]
2. Valid squares (`is_valid_pf`, :36-54): any grid without CAVE_MARK in the player's own map memory is VALID, including the border row/column just past the level edge (the window clips to MAX_WID/MAX_HGT, 198x66, defines.h:82,88). Known grids need `cave_floor_bold`, so known walls, closed doors and rubble block, and known visible traps are excluded. So doors/walls the player hasn't seen are assumed open, and a closed door that is known blocks the route. [SEEN]
3. Monsters. Only the target grid is touched (:93-96, and :106 sets the target open anyway). Monsters in the path are not avoided. The commented-out `#if 0` block (:98-104) would have rejected a non-floor target. The target is always accepted even if it is a known wall. [SEEN]
4. Path to steps. The path is built backward from the target and stored in `p_ptr->pf_result[]` as '0'+(10-dir), with `pf_result_index` pointing at the first step (:162-214). [SEEN] The file is unchanged from the "Pristine MAngband 1.5.3 sources" commit 6963c00 (`git log -- src/server/pathfind.c`). [SEEN]
5. Trigger. Server `recv_pathfind` reads (y,x) bytes (net-game.c:1653-1658) and calls `do_cmd_pathfind` (cmd2.c:3352). Targets within 1 tile become an ordinary walk (:3355-3360). While confused it prints "You are too confused!" and does nothing (:3363-3368). Otherwise `findpath` success sets `running_withpathfind=TRUE; run_request=-1` (:3370-3374). A mouse click goes PKT_MOUSE -> `recv_mouse_hack`, which queues PKT_PATHFIND with the clicked map coordinates (net-game.c:1725-1731). Ctrl-click on an adjacent grid is alter; shift-click on yourself is enter-feature (:1700-1723). Other server triggers: 'g' in look/target mode (xtra2.c:4572, 4682). The tool client has `pathfind Y X` (c-tool.c:34, 680-688). [SEEN]
6. Execution. dungeon.c:1062-1065 calls `run_step` each time the player has full-turn energy while `running || run_request`. In pathfind mode `run_step` calls `run_nextstep` (cmd1.c:2814-2874), which pops one direction at a time and then goes through the normal run move, costing one turn per step like a run. [SEEN] `run_test` (the corridor-following logic) is NOT called in pathfind mode (cmd1.c:2885-2897), so it will not stop at openings, doors or objects. Only `disturb()` stops it. [INFERRED from the code path]
7. Stops. `run_nextstep` aborts and disturbs if the next step is a known wall (cmd1.c:2823-2833, 2842-2848). If the step after next is a known wall, it converts to a normal run in that direction ("walking stick" lookahead, :2850-2866). It also stops when the path is exhausted. `disturb()` (cave.c:4131-4191) clears `running` and `running_withpathfind`. Callers: monster appears or moves in view (monster2.c:1479-1757, gated by DISTURB_MOVE/NEAR), damage, panel change, and others. A PKT_CLEAR also clears pathfind (net-game.c:1774-1775). [SEEN]
8. Walk vs. run. `recv_walk` (net-game.c:1930-1990) drops the current walk if 2 more walks are queued behind it. If `running || resting` it calls `disturb(p,0,1)` and swallows the walk (it stops the run but does nothing itself). Otherwise it walks if energy suffices, else returns 0 and waits. Gap: between `do_cmd_pathfind` (running still FALSE, run_request=-1) and the first `run_step`, a walk is not swallowed. [SEEN; the gap is INFERRED]
9. Run start. `do_cmd_run` (cmd2.c:3090-3150): confused in the dungeon becomes a walk; in town it says "You are too confused!". A wall straight ahead gives "You cannot run in that direction." plus disturb (but EASY_ALTER/BUMP_OPEN may open a door instead). Otherwise it sets `run_request=dir, running=FALSE, ran_tiles=0`. The generic dispatcher (net-game.c:2132) deliberately reports "no energy" for a PKT_RUN that arrives while `running && ran_tiles==0` ("just started running"). That explains the project note that a command sent just as a run starts or ends is ignored. [SEEN; the explanation is INFERRED]
10. Client keys. The roguelike keyset maps shift+hjklyubn (H J K L Y U B N) to '.' + direction (c-util.c:906-914). In the roguelike keyset ',' also maps to run, and digits map to walk ';' (c-util.c:965-1000); the original keyset maps '.' to run (c-util.c:~1015). Server command table: '.' = PKT_RUN with a direction (tables.c:52-55). The client `cmd_run()` sends `Send_run(dir)`. `cmd_walk()` sends `send_walk(dir)` = PKT_WALK + 1 byte (c-cmd.c:594-616, net-client.c:422-425). The mouse path is `cmd_mouseclick` -> `send_mouse(mods, x, y)` in dungeon-relative coordinates (c-cmd.c:1473-1517). PKT_ids: WALK 70, RUN 71, REST 72, PATHFIND 73 (pack.h:68-71). [SEEN] Arrow-key and shift-arrow handling was not traced in the terminal front ends. [NOT CHECKED]
11. Nothing clever in the client. There is no auto-repeat, no run re-issue and no pipelining logic in cmd_walk/cmd_run. Keys go straight into the write buffer, and a human pipelines naturally by key repeat. The run/disturb logic is all server-side. The only client-side "disturb" is `send_clear()` on a first ESC (c-cmd.c:315-320). The in-client `do_cmd_pathfind` (c-cmd0.c:380-420) is inside `#if 0`. There is no '_' or 'h' travel command. '_' is PKT_ENTER_FEAT. [SEEN: grep over client/ for pathfind, PKT_RUN, send_walk]
12. Options (per-player, server-side `option_p`, tables.c:2515-2630): find_ignore_stairs, find_ignore_doors, find_cut, find_examine (all default TRUE) shape `run_test` (cmd1.c:2566-2781). disturb_move, disturb_near, disturb_panel, disturb_state, disturb_minor, disturb_other, disturb_look (default TRUE) gate `disturb()` calls (monster2.c, dungeon.c:238,1518, cmd1.c:1732). always_pickup, easy_alter, bump_open affect run starts and moves. I did not check how options are set from the tool client, and I did not verify disturb_state/disturb_other call sites. Pathfind mode ignores the find_* options (item 6) but still obeys disturb_* options. Turning disturb_near/move off would make runs and pathfinds not stop for monsters (dangerous). [SEEN options; effect INFERRED]
13. Why the Pilot dropped server pathfind (512f394, 2026-09-24). The commit message says: "Server pathfind searches 25 tiles around the player and treats unseen grids as open, including the row/column past the level edge, so near an edge it could route off the level (2S -> 3S). goto() now walks the client-side shortest path itself, keeping two steps queued (the server drops a walk when more than two are queued), one at a time next to the edge; stops and replans on a 'blocking your way' bump, a stall or a deviation." The prior commit 649b3d4 (same evening) had already special-cased "within 2 tiles of the border walk own path tile by tile" after seeing 2S->3S twice at the same spot. [SEEN: git show] The notes add that it "bumps arena walls it hasn't seen" (shopcat/README.md:98-104) and that it is only acceptable in the dungeon "verify before relying on it" (next_steps.md:73-77). Code confirms the cause: pathfind.c:42 plus the clipping at :60-64 (no level-edge check). [SEEN]
14. d682520 (2026-09-25) is not about pathfind. It added Pilot-side runs: straight stretches >=5 are run with '.'+dir and stopped by a walk request one tile before the end. It measured ~0.22-0.29 s/tile vs ~0.5 walking. It is never used near edges or no-go zones. 468b717 only documents the >10 arenas crash and walking speed. [SEEN]
15. Fixability. (a) In the Pilot: use `pathfind` only underground (no level-edge exit; stairs/trapdoors are explicit) or in town only when the destination and all path tiles are known and away from the border; check the first reply by position after each stop. Unknown squares on the route can still be bumped. The Pilot has no use of pathfind at present (no match in tools/pilot). (b) In the server: `is_valid_pf` could reject unknown grids at the level edge, but that is a server change (Architect's call). Do not rely on pathfind for fights: it does not avoid monsters, only the target square. [INFERRED]

## Contradictions and surprises
- Brief's "mouse click travel" is confirmed, but there is no keyboard travel key ('_' / 'h'); the only keyboard route is 'g' in look mode on the server.
- Notes say pathfind "bumps unseen walls". Code: it can only plan through unseen grids and aborts on a known wall. Bumping happens when a step is into an unseen wall. Consistent, but the abort only triggers for known walls (cmd1.c:2823).
- Pathfind mode skips `run_test`, so it is more persistent than a normal run (does not stop at openings), but still stops on any disturb. The Pilot's "runs stop whenever surroundings change" note applies to plain '.' runs, not pathfind.
- The real 1.5.3 server has the ran_tiles==0 "no energy" quirk for a just-started run (net-game.c:2132), which fits the operations.md "command ignored" observation.
