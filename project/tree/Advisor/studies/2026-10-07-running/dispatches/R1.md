# Dispatch: R1 - the server's run algorithm and timing
- Brief: how the server starts, steps and stops a run; energy and real-time cost; town/wilderness edges; sources of unpredictability.
- Clerk run: 2026-10-07; sources: github/src/server/{cmd1.c,cmd2.c,dungeon.c,net-game.c,net-server.c,xtra2.c,cave.c,monster2.c,melee2.c,tables.c,mdefines.h,generate.c}, github/mangband.cfg, git show 6c3cea5/835181c/a516853. (HEAD here is aed11d2, not c97e873; the files read are what is on disk.) All paths below are under github/src/server/.

## Answer
A run is a flag plus a direction. The `.` command (do_cmd_run, cmd2.c:3056) only sets `run_request`. Each game tick (75/s), when the player has a full step of energy, `process_player_end` calls `run_step` (dungeon.c:1061-1066). `run_step` calls `run_test` and then `move_player`. A run step costs exactly the same energy as a walk step (`level_speed`, cmd1.c:2941 vs cmd2.c:3011). Running is faster in real time because the server speeds up the player's clock while running: x5 energy in town (dungeon.c:950-953) and a x5 time bubble in the dungeon and wilderness when no awake monster is in line of sight (xtra2.c:5207, RUNNING_FACTOR=500, mdefines.h:264). It also needs no round trip per step. The run stops on the `run_test` rules, on `disturb()`, or on a walk command arriving.

## Findings
1. **Start** [SEEN]. The run command is a custom command with energy cost 1 (tables.c:52-53). recv_custom_command refuses it (returns 0, so it stays queued) if the player lacks a full step of energy, or if `running && ran_tiles==0` (net-game.c:2131-2142). do_cmd_run (cmd2.c:3056-3150):
   - Refuses a `^.` inscription.
   - When confused, it turns into a walk in the dungeon (cmd2.c:3065-3072) and is refused in town ("You are too confused!").
   - It returns silently if already running in the same direction (cmd2.c:3083).
   - If the adjacent grid in that direction is a *known* wall/door/etc. and there is enough energy, it prints "You cannot run in that direction." and disturbs (cmd2.c:3088-3135). With easy_alter or bump_open it opens/alters the door instead.
   - Otherwise it sets `run_request=dir`, `running=FALSE`, `ran_tiles=0`. It returns 1, which lets the command loop keep reading further queued commands (net-game.c:2418-2425).
2. **First step** [SEEN]. run_step (cmd1.c:2879-2950) takes the `run_request` branch: run_init, then `running=TRUE`. **The first step skips run_test**, so it goes straight to move_player. A visible monster adjacent in that direction is attacked, and a shop door is entered [INFERRED from move_player cmd1.c:1790-1800, 1965-1972]. Later steps call run_test first and stop on TRUE with `disturb()` (cmd1.c:2919-2927). Each step adds noise (cmd1.c:2932), calls move_player, subtracts `level_speed` energy unless blows were dealt, and zeroes `energy_buildup` (cmd1.c:2936-2950).
3. **Time and energy** [SEEN]. Per tick the player gets `extract_energy[speed]` (1000 at normal speed, tables.c:2184), capped at `level_speed(depth)` (dungeon.c:931-985). `level_speed(0)` = 7500*5 = 37500 (xtra2.c:5109-5113, tables.c:2204). Depth 1 is 9000*5 = 45000. With FPS=75 (mangband.cfg:67) a town step takes 37.5 ticks, about 0.5 s, and a depth-1 step about 0.6 s. This matches the measured 2.2 tiles/s walking. Running in town gets energy x5 (dungeon.c:950-953), about 0.1 s/step, matching "0.11 s/tile". In the dungeon and wilderness, `time_factor` is 500% while `running && !monsters_in_los` (xtra2.c:5207). It returns 100 in town only (xtra2.c:5259). `monsters_in_los` counts only *awake* monsters with `mon_los` and hostile players (xtra2.c:5116-5147). Monsters near the player also get x5 energy (melee2.c:3463-3466), so relative speed is unchanged.
4. **Why walk-per-command is slower** [SEEN + INFERRED]. recv_walk returns 0 (kept in queue) if energy < a full step, and 3 ("all energy used, break loop") after a walk (net-game.c:1950-1975), so at most one walk executes per energy fill. Commands run at network arrival (`post_process_players`, net-server.c:461-480) and again in `process_player_end` (dungeon.c:1022). A walk costs the bot a round trip plus up to one tick of quantisation per step. Walking also resets `energy_buildup` (net-game.c:1965-1969), so the buildup bonus never applies. Several walks queued ahead: "if two more walks are queued behind the head one, skip the head" (net-game.c:1918-1926). Walks are cheap to send but gain nothing from queueing.
5. **A walk cancels a run** [SEEN]. recv_walk: `if running||resting: disturb(p_ptr,0,1); return 1` (net-game.c:1932-1936). The walk is swallowed. Explanation for "command sent as a run ends is sometimes ignored" [INFERRED]: the last step has been taken, but `running` stays TRUE until the next run_test call, which needs a new full step of energy. A walk arriving in between is eaten as the cancel. A new `.` in the same direction is eaten too (cmd2.c:3083).
6. **Pathfind runs** [SEEN]. `pathfind Y X` sets `running_withpathfind` and `run_request=-1` (cmd2.c:3370-3373). run_step then follows the stored path via run_nextstep (cmd1.c:2814-2870) and **never calls run_test**. Only disturb() and "known wall next" stop it. It converts to a normal run if the step after next is a known wall (cmd1.c:2850-2866).
7. **run_test rules** [SEEN, cmd1.c:2452-2780]. It looks only at the 3 (straight) or 5 (diagonal) newly adjacent grids ahead.
   - **Returns TRUE (stop)** if any of those grids has a *visible* monster (cmd1.c:2488), a visible object (2494), or water (2499).
   - It also stops for any **remembered** (CAVE_MARK) feature not in the ignore list. That covers closed doors, rubble, traps, shop entrances, lava, passable rubble. Ignored: floor, secret/invisible, veins, grass/tree/dirt, all walls. Open/broken doors and stairs are ignored only if find_ignore_doors / find_ignore_stairs are on (both default TRUE, tables.c:2732-2736).
   - Corridor mode (walls on both sides at start): follows single bends. It stops at no options (dead end), at 3 options or 2 non-adjacent options (junction), and at room entrances; the two-option rules depend on find_examine/find_cut (default TRUE) (cmd1.c:2677-2741).
   - Open-area mode (default in rooms): ignores unknown/floor grids but sets break_left/right when a wall appears on a side. It stops when that side opens up again (cmd1.c:2620-2669). Result: running along a lit room wall stops at doorways. Open dark rooms behave differently because far walls are unknown.
   - Final check: stop if a *known* wall is directly ahead (cmd1.c:2745).
   - Ghosts never stop (cmd1.c:2470).
8. **Town/wilderness** [SEEN]. In run_init, run_test and see_wall every break_left/right setting is skipped when `dun_depth <= 0`, so open-area mode stays on for the whole run. In town and wilderness the run therefore stops only for the stop conditions in finding 7 (visible monster/object, water, noticeable feature) and a known wall straight ahead. A wall that is not CAVE_MARK, such as the town boundary at night or unlit trees, is not a wall to the algorithm. Out-of-bounds grids count as open floor (cmd1.c:2548, "wilderness hack"; see_wall cmd1.c:2108-2109). `in_bounds` is the same rectangle for depth 0 (mdefines.h:2793). Moving off the map (y<=0, x<=0, y>=65, x>=197) is not blocked unless `cfg_town_wall` or `cfg_ironman`; the shipped cfg has TOWN_WALL=false (mangband.cfg:145). The player then moves to the neighbouring wilderness sector (cmd1.c:1640-1730). `disturb()` fires there only if disturb_panel is on (cmd1.c:1732, default TRUE). Otherwise `running` stays TRUE, `new_level_flag` makes run_step return for a tick (cmd1.c:2881), and the run continues in the new sector [INFERRED]. This is the likeliest mechanism for the 10-07 incident. I did not check the pilot's option values; commit 6c3cea5's message says disturb_move/near are off as the user plays. The world edge produces "Walls of the World" and disturb (cmd1.c:1699).
9. **Stairs and doors** [SEEN]. With find_ignore_stairs TRUE (default), a run goes over stairs, including the town's dungeon entrance, without stopping. A run never takes stairs. Entering a shop: a run into a shop door gets "bump" handling (cmd1.c:1965-1972) and disturb. Closed shop doors that are remembered stop the run one tile short via run_test.
10. **Monster disturb gates** [SEEN]. With disturb_move/disturb_near ON (defaults), a monster that appears or disappears, or moves while visible/in view, calls disturb (monster2.c:1479,1511,1529,1543; melee2.c:3139-3146). Monster spell/shriek messages call disturb(1) unconditionally (melee2.c:569-1956). The tool pilot has these OFF (per commit message, not verified), so only run_test's adjacent-grid check, damage and spells stop a run. A monster coming from far away is then **not** a stop trigger. Also, with no awake monster in LOS the time bubble is x5, and the first awake monster in LOS drops it to x1 instantly (xtra2.c:5207).
11. **Other stops** [SEEN, see table]. Damage (take_hit, spells1.c:567), traps found or triggered, objects picked up, level feelings (DISTURB_MINOR), light going out, word of recall, hunger faint, status changes (DISTURB_STATE, xtra2.c passim). The Dungeon Master is exempt (cave.c:4140).
12. **Unpredictable for a program** [INFERRED]. (a) Length: the stop point depends on which grids are CAVE_MARK, which depends on light radius and day/night. (b) The server rewrites direction in corridors: `find_current` changes, so the final position is not on the commanded line. (c) Pathfind runs ignore run_test. (d) First step is unchecked. (e) Options (find_*, disturb_*) are per player. (f) The time bubble means monsters near you also move x5 while you run.

## Contradictions and surprises
- next_steps.md says "walking resets built-up energy". Confirmed (net-game.c:1965-1969, cmd1.c:2950).
- operations.md says "the server's run logic stops whenever surroundings change (openings, monsters, objects)". That is true in the dungeon, but in town/wilderness nearly nothing stops a run (finding 8).
- The 5x speed-up is in game time, not in packet latency. The measured 2.5x (5.5 vs 2.2 tiles/s) is below the theoretical 5x for runs in town because of stops and restarts [INFERRED].
- Another dispatch (R2) cites cmd1.c:2566-2781 for run_test; in this checkout it is cmd1.c:2452-2780.
