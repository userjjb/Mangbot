# Dispatch: S1 - what can be staged, and replay inputs
- Brief: DM/wizard powers on the test server, whether a level can be staged reproducibly, and what records exist to replay the Pilot's decision code.
- Clerk run: 2026-10-22; sources covered: github/src/server (xtra2.c DM menu 5960-7340, birth.c, cmd1/2.c, monster2.c, generate.c, load2/save.c, dungeon.c, control.c, tables.c, mdefines.h), src/client/c-tool.c, testserver/mangband.cfg and save/, tools/pilot/{world.py,pilot.py logging,replay_group.py}, runs/pilot/dive04 logs, runs/missions.json.

## Answer
1. The only staging tool is the "&" Dungeon Master menu, which belongs to the character named in `DUNGEON_MASTER_NAME` (Gandalf, already set). It can place any monster (awake, with its group) and any terrain feature, stamp vaults, edit a pack item's pluses and ego, delete monsters and objects, pull Dive04 to Gandalf's square, make a level static, and export or import a level's terrain file.
2. It cannot set Dive04's HP, stats or pack directly, place a named item on the floor, or fix a seed.
3. The headless tool client (c-tool.c) answers the DM menu with ESC. Gandalf cannot be scripted until a "send key" verb is added or the interactive client is used.
4. A replay can reconstruct position, depth, HP, messages, the monster list and the flags grid. It cannot reconstruct the map as the Pilot remembered it at second T, nor the pack or equipment. Both come from polled query replies that are deliberately not logged.

## Findings (beyond the table)
1. Menu text and flags: Gandalf's page access uses the `dm_access` table, all granted by 0xFFFFFFFF. [SEEN] (xtra2.c:5992-6000)
2. Monster placement uses the generator's race list directly, so any r_idx in monster.txt (about 618) can be placed, including level-appropriate and out-of-depth ones. [SEEN] (xtra2.c:6118-6160; monster.raw max_r_idx 618 in the Dive04 save)
4. Door states, secret doors and rubble can be built as features (indices 32-49). Doors "locked/jammed" strength is part of the index. [SEEN]
5. Arenas exist in wilderness.c (FEAT_PVP_ARENA, 30% of large houses) but are PvP boxes, not a staging tool. [SEEN] (wilderness.c:1136-1175)

## Replay inputs
Per tick the Pilot reads: pos, depth, map rows+attrs (query, 0.5 s), status indicators (0.3 s: HP, hunger, level, track, state), inventory (10 s or on change), flags grid (10 s), floor item (1 s), monlist/itemlist events, messages (world.py:22-75, 247-300).

What is logged:
| record | where | content | gap |
|---|---|---|---|
| pos, message, level, monlist, itemlist, flags, floor, store, confirm, ack | events.jsonl | every packet event with `epoch` (since 10-09). Flags and floor replies are logged | **map, status, inven, options, commands are skipped** (pilot.py:4838-4841). About 237k of 934k events have no `epoch` (m15, m16) and need alignment as replay_group.py does |
| mons (1/s while monsters in view in dungeon) | decisions.jsonl | `[y,x,name]` list, `track` health bar, `fighting` | Only when monsters present; no colour/attr, no sleeping flag |

| levels/*.txt (136 files, m17+) | levels/ | remembered terrain+item glyphs of the whole level, written **when leaving** | One frame at exit, so it holds knowledge from after second T. No monsters, no colours; m15/m16 have none |
Counts per window (m17-m23): `mons` 108-598, `pos` 1.7k-5.1k, `monlist` 266-1075 (decisions.jsonl and events.jsonl, windows from missions.json).

## Contradictions and surprises
- Surprise: c-tool.c cannot drive the DM menu at all (c-tool.c:351-358). The Advisor's brief assumed "a client to send them". The interactive client (c-cmd.c:1060 `send_term_key`) can.
- The pre-designed levels in save/ look usable but are inert: they load only in Ironman/More-towns (load2.c:1636).
- Saved levels hold no monsters or objects, so a "saved arena" does not store a setup. Monsters must be re-placed each time (hooks, or a script of keys).
- next_steps.md and operations.md say not to use Gandalf as a stand-in player (next_steps.md:94,809). That fits: he is a ghost.
