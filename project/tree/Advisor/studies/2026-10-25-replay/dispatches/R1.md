All 12 replay files are written. ## Findings
1. **Clock model [SEEN world.py:40-116, pilot.py:5412-5436].** `_CLOCK` holds wall, game, factor, model, measured, fast_ok, rate. `gnow()` calls `_advance`, which does `game += (wall_now - wall_last) * factor`. `_set_factor` records the change in `_HIST` (wall, game, factor) so `wall_at(g)` can invert it.
   - The factor is the model, 1.0 (town, normal) or 0.2 in the dungeon when HP% <= hpwarn x 10, with hpwarn defaulting to 5 (the user, 10-24; `--hpwarn`). The model is set each `tick()`.
   - While resting or running with no monster in view, `fast_ok` is on, and the factor is the rate measured from the light's fuel: `(fuel_change) x TICK_S(0.625 s) / wall_dt`, clamped 0.05..20, stale after 12 s (`STALE_S`). It then falls back to the model.
   - Game timers use `gnow()`; network timers use `wall_since(g)`.
   - The comment at world.py:18-19 says the server (xtra2.c base_time_factor) runs 1/5 below hitpoint_warn x 10% HP and up to ~10x resting and 5x running with nothing in view. I did not check xtra2.c (server code is out of scope).
2. **One player turn in wall seconds [SEEN, my measurements].**
   - m17-m23 (no time_factor logged, so these are factor 1.0 [INFERRED]): the median interval between successive one-square pos events was 0.67 s (n=337, 10th-90th percentile 0.13-1.3 s). The mode bin is 0.6-0.8 s (190 of ~330 intervals). The first logged walk (start of the run) gave 0.50 s. The step interval is paced by the Pilot, so it is an upper bound on the game turn at normal speed.
   - Interval between consecutive item-command effects (Phase, cures, WoR): median 1.25 s, range 0.52-12.0 s (n=72).
   - Latency from command logged to confirming message: median 0.56 s, range 0.003-1.78 s (n=82). No slowdown at HP < 30% (3 samples).
   - Later missions, same matching rule on E1's evs.pkl [SEEN, read-only, outside my 12 episodes]: at factor 1.0 (n=26), latency median 0.99 s, range 0-8.7 s. At factor 0.2 (n=30), latency median 3.2 s, range 0.01-25.5 s, 10-90% 2.0-16.0 s. Interval between consecutive item effects: factor 1.0 median 4.0 s (1.25-11.25, n=11); factor 0.2 median 5.0 s (1.7-26.5, n=21).
   - So one item turn is about 0.6-1.3 s at 1.0 and 3-5 s at 0.2, with a long tail to about 25 s. This matches E1's 4-19 s command latency in the bubble.
3. **No `time_factor` records exist before m24 [SEEN, all 12 episodes: empty list].** hpwarn was not in effect then. No slowdown shows at 25-36% HP (ep0 lowest 64/177, ep8 61/241), so I treat m17-m22 as factor 1.0 throughout [INFERRED].
4. **Inventory check.** Counts (CLW/CSW/CCW) agree with the "quaff N Potions" count in the first cure act after t0 in every episode that has one (11 of 12; ep11 has none). The other items (phase, wor, tele, hero...) rely on "You have N X." messages. Discounted stacks ("{75% off}") are separate stacks, so a count may cover one stack only.

## Contradictions and surprises

In ep4 the rule's t0 (22:24:41) falls 0.2 s after the Ranger summoned animals (22:24:40.8) and 1.7 s after fight start (22:24:39.1, HP 220/220). I added a field `t_pre` (earlier of the two candidates, clamped to 60 s). Messages, kills and actions are listed from `t_pre`, so t0 stays the rule's value while nothing just before it is lost.
- E1's resend-duplication finding cannot be tested here: no m17-m23 episode has time_factor records or "resend" acts.
- Status booleans are false only if no on-message is seen in the 30 min before t0 (state.jsonl status is game-clock, not merged).

## Leads
- hpwarn was off in the m17-m22 era: E1's counts and any simulator calibration against them use real-time (factor 1.0) fights. Fights in m24+ at factor 0.2 give 3-5 s per item turn. These two eras should not be pooled.
