# New memo: why the Pilot walks, and how to make it run (Advisor → Architect, 2026-10-07)

The user asked: `memos/2026-10-07-running.md`. The short version:

1. **82% of dungeon runs are cancelled before their first step.** A run waits for a full turn of energy (0.6–0.67 s
   below town), but `_free_tick` gives up after 0.5 s and the next walk cancels the run (`mover.py:175`,
   `net-game.c:1932`). Wait ~1.0 s (dungeon) / 0.7 s (town) for the first step and send no walk meanwhile.
   This alone should roughly double dungeon travel speed.
2. **Running is 5× faster because the server speeds up time while running** (`xtra2.c:5207`, `dungeon.c:949-953`): 0.107 s/tile
   against 0.507 walking in town.
3. **Both surface incidents (10-07 09:19 left the map; the mission-13 shop-5 loop, which was 185 runs) were unbounded *free*
   runs at night.** The server treats unmarked ground and the map edge as open (`cmd1.c:2548`, TOWN_WALL=false). Re-enable
   surface *stretch* runs with an edge guard, keep free runs off the surface, bound free runs by progress toward the
   goal, and count them as replans.
4. Set `disturb_panel`/`disturb_near`/`disturb_move` explicitly at login (the Pilot sets none today).
5. Optional: server `pathfind` in the dungeon for long known routes (it doesn't stop at junctions).
