# Memo: why the Pilot walks, and how to make it run (Advisor → Architect, 2026-10-07)

**The user:** "The Pilot often walks, this is often because in past cases running causes issues. A human
player can run with minimal issues. What can be done about this?"
**Audit trail:** `Advisor/studies/2026-10-07-running/` (R1 server run code, R2 pathfind and client, R3 Pilot
movement and history, R4 all 14,100 runs in the Dive03/Dive04 logs → `scratch/R4_runs.csv`).

## 1. The answer in four points

1. **A run is 5× faster because the server speeds up time while you run.** It isn't packet savings. With no awake
   monster in line of sight, `time_factor` = 500% while running (`xtra2.c:5207`). In town, running gives ×5 energy
   (`dungeon.c:949-953`, `RUNNING_FACTOR 500`) **[code ✓]**. A run step costs the same energy as a walk step. Measured:
   **0.107 s/tile running in town against 0.507 walking; 0.133 against 0.61–0.67 at 100–750 ft** (R4).
2. **In the dungeon the Pilot already tries to run a lot, but 82% of its runs never get going.** 13,194 dungeon runs:
   6,879 moved 0 tiles and 3,881 moved 1 tile before the Pilot gave up. A run waits on the server until the player has a full
   turn of energy (0.6–0.67 s in the dungeon). `_free_tick` gives up after **0.5 s** without movement (`mover.py:175`)
   **[code ✓]**, replans, and sends a walk. A walk to a running player is swallowed as "stop" (`net-game.c:1932`).
   Runs sent < 0.15 s after a step started only 11% of the time; runs sent ≥ 0.5 s after a step started 44% of the time. **This is the main
   reason the Pilot "walks": its runs are cancelled before they start.** A human presses the key and waits.
3. **The surface failures were one bug, and it's fixable:** an unbounded *free* run (`free_run(keep_goals=True)`) over
   unknown ground at night. In town the server's run logic ignores walls it hasn't marked and treats squares past the
   map edge as open floor (the "wilderness hack", `cmd1.c:2548`, `see_wall` `cmd1.c:2108`). `TOWN_WALL = false` on both servers
   **[code ✓]**, so a run walks off the town map into the next sector. Both incidents follow this pattern:
   - 10-07 09:19: a free run went 133 tiles west in 14 s to −200 ft.
   - Mission 13's shop-5 loop: **185** runs (not 94), free runs bouncing between y=27 and y=48 on x=114. The goal squares
     were at x=111, so `resume_goals` never matched, and free runs use no replan budget (`mover.py:181`).
   - Dive03 on 09-25 22:34 did the same, which is why 66971c5 stopped explore on the surface.
   Stretch runs (straight path, stopped one tile early) behaved: town stretch runs overshoot 0–1 tiles (R4).
4. **Server pathfind** (the human's mouse-click travel) is a run along a server-planned path at run speed. It skips the
   junction and opening stops and halts only on `disturb()` (`cmd1.c:2814-2897`). It was dropped (512f394) because it treats
   never-seen squares, including the row past the level edge, as open (`pathfind.c:36-64`) **[code ✓]**. It's usable in
   the dungeon only when the Pilot has checked that the route is over known squares (§2.6).

**How much it buys:** movement is ~10–20% of active mission time (walk steps alone are 2.3 h of Dive03's 15.4 h).
Dungeon movement now averages 1.8–2.6 tiles/s, and runs that start reach 3.2–3.5 tiles/s including launch and stop. Fixing
the starved runs should roughly double dungeon travel speed (saving ~5–10% of mission time). Town errands would go
from ~2 to ~5–9 tiles/s. The bigger time sinks remain town waits and Navigator gaps (G4 study).

## 2. Changes (yours to decide; most valuable first)

1. **Don't starve runs.** After sending a run, wait for the first step for at least one energy period plus margin
   (~1.0 s in the dungeon, ~0.7 s in town; or compute `level_speed(depth)/1000/75 × 1.3` s) before deciding it
   failed. During that window send no walk (it would cancel the run). Alternatively, send the run only ≥ 0.6 s after
   the last step, when the energy is full. Apply this to `_run_tick` (0.8 s, probably OK in town, borderline at depth) and
   `_free_tick` (0.5 s, too short everywhere below town).
2. **Re-enable runs on the surface, as stretch runs only:**
   - **no free runs on the surface** (no `free_run` from Goto or Mover when `in_dungeon` is False);
   - a stretch run only when its end tile is known, the stretch stays ≥ 3 tiles from the map edge
     (rows 1..64, cols 1..196), and the stop is sent one tile early as now;
   - at night, also require the end tile to be marked (`CAVE_MARK`: seen), not just plannable.
   This keeps the 10-07 protection and gets town errands back to ~5× speed.
3. **Bound every free run:** stop it (`walk 5`) when it moves away from the goals (distance to the nearest goal grows
   for 2 steps) or leaves the planned path's corridor. Count each free run against `max_replans`. Remove the Shop
   exemption from `watch_progress` (`pilot.py:1932`), or add "N runs without getting closer" as a stuck test.
4. **Set the run options at login**, explicitly, with the tool's `option NAME yes|no` (`c-tool.c:774`). The Pilot sets
   none today, so behaviour depends on the saved character.
   - `disturb_panel yes`: a run that crosses a sector edge stops on arrival (`cmd1.c:1732`). It's a backstop, not a guard.
   - `disturb_near yes` and `disturb_move yes`: the server stops a run the moment a monster comes into view or moves.
     That's faster than the Pilot's polling: at ×5 time it covers ~3 tiles per 0.3 s poll. The 6c3cea5 note says these are off "as the user
     plays". Check and decide. With them on, the Pilot's own "monster within 5" stop can stay as a second check.
   - Keep `find_ignore_stairs`, `find_ignore_doors`, `find_cut`, `find_examine` at their defaults (on).
5. **Don't start a run toward an adjacent monster or a shop door.** The first run step skips `run_test` (`cmd1.c:2904-2915`),
   so it attacks or enters.
6. **Optional, dungeon only: server pathfind for long known routes.** Send `pathfind Y X` when the target is within the
   ±25-tile window, every tile of the Pilot's own path is known floor, and no monster is in view. Then watch `pos`, and
   stop with `walk 5` if the route leaves the Pilot's path (the server may choose a shorter path through unknown squares).
   It skips junction stops, so one command can cover a whole multi-turn corridor at run speed. It's an experiment: do 1–3 first.
7. **Fix the docs:** next_steps.md and operations.md say runs are for straight stretches ≥ 5; RUN_MIN has been 3 since
   6c3cea5. Also: "a command sent as a run starts or ends is ignored" is two documented server behaviours: a run arriving while
   `running && ran_tiles == 0` waits (`net-game.c:2132`), and a walk while running is eaten as the stop (`net-game.c:1932`).

## 3. What a human does differently

A human presses shift+direction (PKT_RUN) and waits. They don't time out at 0.5 s, they don't send a walk into a run
that hasn't started, and they don't run toward unseen ground at the edge of town at night, because they can see the
screen. The client does nothing clever: no auto-repeat or pipelining; the run and disturb logic is all server-side (R2). The
fixes above give the Pilot the same patience and the same caution.

## 4. Coverage and gaps

- Lit room, dark room and corridor runs can't be told apart in the logs (no map snapshots). The 82% starvation figure covers all
  dungeon runs.
- The character's current option values (disturb_*, find_*) weren't read. One `options` query settles it.
- Not identified: what stopped the shop-5 runs at y=48 (y=27 is probably shop 4's door).
- Expected gains are estimates from the logged step timings, not a trial. A before/after mission with change 1 would measure it.
